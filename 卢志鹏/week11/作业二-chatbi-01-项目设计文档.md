## 1. 项目背景与问题定义

### 1.1 业务痛点

企业数据消费的典型现状：

1. **取数链路长**：业务人员有数据需求时，需要提工单给数据分析师，分析师写 SQL、跑数、回传 Excel，平均响应以小时/天计；
2. **报表固化**：BI 报表按预设维度开发，临时性、探索性的问题（"上周华东区的销量为什么跌了？"）无法通过固定报表回答；
3. **口径不统一**：同一指标（如"销售额"）在不同报表中口径各异（含不含退款、含不含赠品），数据可信度受损；
4. **工具门槛高**：拖拽式 BI 工具仍要求使用者理解表结构与维度模型，业务人员难以自助。

### 1.2 技术机会

大语言模型的成熟使**自然语言即查询接口**成为可能：

- NL2SQL 能力：将自然语言问题转为可执行 SQL；
- 多轮对话能力：支持追问、修改条件、对比分析；
- 代码与图表生成能力：根据数据特征自动选择可视化形式并生成结论摘要。

### 1.3 问题定义

构建一个 ChatBI 系统，使业务人员能够**通过自然语言对话完成数据查询、可视化与初步归因分析**，同时保证**口径统一、结果准确、数据安全**。

## 2. 项目目标与成功指标

### 2.1 项目目标

1. **自助取数**：覆盖 80% 的日常取数类问题，业务人员无需分析师介入；
2. **口径统一**：核心指标通过语义层统一定义，一数一源；
3. **可信可查**：问答过程透明（可查看 SQL 与口径），准确性可度量、可持续优化。

### 2.2 成功指标（北极星 + 护栏）

| 类别 | 指标 | V1 目标 | 说明 |
|---|---|---|---|
| 准确性 | 评测集执行准确率 | ≥ 85% | 生成的 SQL 与标准 SQL 执行结果一致 |
| 准确性 | 评测集结果准确率 | ≥ 80% | 最终自然语言答案数值正确 |
| 效率 | 单次问答平均响应 | < 10s | 含 SQL 执行与总结 |
| 采用 | 周活跃提问用户 | 上线 3 个月内 ≥ 50 | — |
| 采用 | 业务自助取数占比 | ≥ 60% | 提数工单量下降比例 |
| 护栏 | 越权/注入拦截率 | 100% | 安全测试用例全拦截 |

## 3. 目标用户与使用场景

### 3.1 目标用户

| 用户角色 | 特征 | 核心诉求 |
|---|---|---|
| 业务运营/市场人员 | 不懂 SQL，懂数务问题 | 快速取数、看趋势、做对比 |
| 业务负责人/管理层 | 只看结论 | 关键指标问答、异动原因 |
| 数据分析师 | 会 SQL | 减少重复取数，聚焦深度分析 |

### 3.2 典型场景（示例数据源：chinook 音乐商店）

> 本项目以课程示例数据库 chinook（专辑/艺术家/客户/订单）作为演示数据源，业务场景类比为"数字音乐商城的运营分析"。

| 编号 | 场景 | 用户提问示例 | 期望输出 |
|---|---|---|---|
| S1 | 单指标查询 | "一共有多少张专辑？" | 数值 + 结论句 |
| S2 | 分组统计 | "各流派的歌曲数量是多少？画个柱状图" | 分组表格 + 柱状图 |
| S3 | 排序 TopN | "销售额前 10 的客户是谁？" | 排名列表 |
| S4 | 多表关联 | "美国客户的订单总金额是多少？" | 数值（跨 invoices/customers） |
| S5 | 趋势分析 | "按月看 2013 年的销售额走势" | 折线图 + 趋势描述 |
| S6 | 追问（多轮） | （接 S5）"那 2013 年 Q4 呢？换个柱状图" | 继承上文条件的结果 |
| S7 | 归因初探 | "为什么这个月销售额下降了？" | 按维度拆解 + 初步归因 |

## 4. 业界现状分析

| 产品 | 形态 | 可借鉴点 |
|---|---|---|
| Power BI Copilot | BI 内嵌对话 | 与既有报表体系融合、数据问答 + 报告生成 |
| Tableau Pulse / Agent | 指标层 + 主动洞察 | 指标为核心对象、异动自动解释 |
| 阿里 Quick BI 智能问数 | 独立问答模块 | 语义层管控、权限继承、问答评测运营 |
| ChatGPT 高级数据分析 | 对话 + 代码解释器 | 代码执行兜底复杂计算（本项目 Data Agent 部分承接） |

**结论**：业界共识 = NL2SQL 只是入口，**语义层 + 评测运营 + 过程透明**才是可用性分水岭。本项目设计遵循该共识。

## 5. 产品定位与边界

### 5.1 定位

面向内部业务团队的**对话式数据问答与分析入口**，定位为"取数与分析的加速器"，不替代数据仓库与正式报表体系。

### 5.2 范围内（In Scope）

- 数据问答（NL2SQL → 执行 → 总结 → 图表）；
- 多轮对话与上下文继承；
- 语义层/指标管理（后台功能）；
- 数据权限与安全；
- 问答质量评测与反馈闭环。

### 5.3 范围外（Out of Scope）

- 写入/修改业务数据（系统只读）；
- 复杂建模与预测（由姊妹项目 **Data Agent** 承接，见 `../data-agent/`）；
- 报表设计器、ETL 开发（既有工具覆盖）。

> **与 Data Agent 的关系**：ChatBI 解决"问数据"（快速、准确地取数与呈现）；Data Agent 解决"做任务"（自主规划、代码执行、完成端到端数据分析任务）。ChatBI 是 Data Agent 的能力子集与快路径，二者共享语义层与 SQL 生成底座。

## 6. 总体方案概述

核心思路：**"语义层 + 多阶段生成 + 校验闭环 + 透明呈现"**。

```
用户提问
   │
   ▼
意图识别与改写（歧义澄清、指代消解）
   │
   ▼
Schema 感知与表选择 ──► 语义层/指标定义 + Few-shot 示例注入
   │
   ▼
NL2SQL 生成 ──► 静态检查（AST）──► 试执行 ──失败──► SQL 自修复重写（≤N次）
   │                                          │
   ▼ 成功                                     │
执行查询（权限注入、只读账号）◄────────────────┘
   │
   ▼
结果总结 + 图表推荐（NL2Viz）
   │
   ▼
回答呈现（结论 + 图表卡片 + 可展开的 SQL/口径/耗时）
   │
   ▼
反馈采集（点赞/点踩 → Bad case 池 → 评测集回流）
```

技术底座沿用课程 Demo 验证过的链路（Qwen 系列模型 + OpenAI Agents SDK + SQLAlchemy 元数据解析），在其上补齐语义层、权限、评测与产品化封装。

## 7. 版本规划

| 版本 | 主题 | 核心内容 | 验收要点 |
|---|---|---|---|
| **V1（MVP，4 周）** | 单轮问答可用 | Schema 感知（DBParser）、表选择 Agent、SQL 生成、SQL 校验与自修复、结果总结、基础图表、评测集 v1（≥200 条） | 评测准确率 ≥85%；演示链路打通 chinook |
| **V2（+6 周）** | 可运营 | 多轮对话、语义层/指标管理、行/列级权限、Few-shot 向量检索、反馈闭环 | 口径冲突率显著下降；点踩闭环跑通 |
| **V3（+8 周）** | 分析增值 | 归因分析（维度拆解）、异动洞察、主动推送、优质问答沉淀看板 | 归因场景覆盖率与采纳率 |

## 8. 风险与应对

| 风险 | 等级 | 影响 | 应对 |
|---|---|---|---|
| NL2SQL 幻觉（表/字段编造） | 高 | 结果错误，信任崩塌 | Schema 严格注入 + 仅允许引用给定元数据；校验拦截 |
| 口径不一致 | 高 | 一数多值 | 语义层强制引用指标定义；口径可展开查看 |
| 复杂多表问题准确率低 | 中 | 部分问题答不出 | Few-shot 增强；识别后降级引导（"该问题较复杂，建议…"）并转 Data Agent |
| 数据越权 | 高 | 合规事故 | 只读账号 + AST 检查 + 权限强制注入三道防线 |
| 响应慢/成本高 | 中 | 体验差 | 模型分级（qwen-plus/qwen-max）、结果缓存、流式输出 |
| Prompt/模型迭代无回归 | 中 | 线上质量回退 | 评测集 CI 化，任何变更跑回归 |
