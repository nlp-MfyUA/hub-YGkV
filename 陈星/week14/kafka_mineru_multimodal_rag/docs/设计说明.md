# 设计说明

## 一、作业要求怎么落到代码

| 要求 | 代码位置 | 说明 |
| --- | --- | --- |
| 网页上传多个 PDF | `app.html`、`app.py: upload()` | 1~10 个文件，校验扩展名与 `%PDF-` 文件头，整体失败时删除已写文件 |
| 通过 Kafka 到后端 | `app.py: upload() → outbox`、`dispatch()` | 上传事务里同时写 `documents` 与 `outbox`，后台发布器把 `{event_id, doc_id}` 发到 `pdf.parse.v1` |
| 后端用 MinerU 解析并存储 | `app.py: worker() → process_event() → run_mineru() → build_chunks()` | 原 PDF、MinerU 输出、图片、文字块与向量都落盘/入库 |
| 显示待解析 / 解析中 / 解析完成 | `documents.status`、`app.html: poll()` | `queued → processing → ready`，失败是 `failed` 可重试；页面每 2 秒查询 |
| 图文混排回答 | `app.py: chat()`、`app.html: render` | 模型返回 `blocks`（文字/图片交错），图片 URL 由后端从检索结果生成 |
| 图问 + 文问 | `app.py: chat()` | 用户图片先转文字描述参与检索，原图 + 问题 + 证据 + 命中文档图一起送视觉模型 |
| 作业1 Redis 存对话历史 | `app.py: ChatHistory`、`redis_demo/redis_demo.py`、`/sessions` | List + LTRIM + EXPIRE；Redis 不可用时退回内存 |
| 作业1 Kafka 传消息 | `redis_demo/kafka_demo.py` | 任务主题 → 处理 → 结果主题；Redis SETNX 去重 |

## 二、为什么用 outbox

上传接口需要尽快返回，而“库里已经有这条任务、Kafka 没收到消息”会让任务永久卡住。
所以同一事务里写文档记录和待发送事件，发布器成功发送后才标记 `sent=1`。进程在发送后、标记前崩溃
可能重复发送，worker 用 `event_id` 和终态检查跳过重复。

## 三、解析与索引

1. `run_mineru()` 调用 MinerU，输出格式随版本不同：
   - 2.x pipeline：`*_content_list.json`；
   - 4.x：`mineru parse` 输出的 Markdown（带页码注释、表格）或 `middle.json`（`pages/blocks/content`）；
   - 自建 parse-server 返回的 zip 包会先解包再取 `middle_json.json`。
   `find_content_list()` 统一识别，`markdown_items()` / `middle_items()` 转成同一种块列表。
2. 图片：4.x 的 Markdown 里图片是 `doc:.../page:N/block:M` 定位符，`fetch_located_image()` 再调
   `mineru read` 取出 PNG，转成 JPEG 存 `data/media/`，并让视觉模型生成描述。
3. 切块：900 字、重叠 150 字；图片块把“图注 + 描述 + 相邻文字”拼进检索文本，保证图片也能被文字检索到。
4. 一个事务里写块与向量、改状态为 `ready`，索引没写成功就不会显示完成。

## 四、问答

1. 取所有 `ready` 且向量模型一致的块，算余弦相似度取前 5；
2. 提示词要求模型只返回 `{"blocks":[{"type":"text"...},{"type":"image","source_id":"S1"}]}`；
3. 后端只接受本次检索到的图片来源，模型给的 URL 一律忽略；
4. 同一 `session_id` 的最近几轮问答写入 Redis，并作为参考带给模型（证据仍来自检索）。

## 五、已知限制

- 单机演示：单 API、单 worker、无登录；多人或扩 worker 需要任务租约、权限过滤和消费组协调；
- SQLite 全量算相似度，只适合小规模；没有重排和相关度阈值；
- 图片走“描述辅助文本检索”，没有图文统一向量；
- 解析大 PDF 时 CPU 版 MinerU 耗时较长（本机 basic 档约 1 分钟/页量级，视页面复杂度而定）。
