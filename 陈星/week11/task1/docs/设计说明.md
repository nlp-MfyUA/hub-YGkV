# SQL Agent Workflow 设计说明

## 一、设计目标

给定用户自然语言问题和 `chinook.db`，依次实现：

`数据库解析 → Table 选择 →（关联表补全）→ SQL 生成 → SQL 校验 → SQL 改写 → SQL 执行 → 结果汇总`

该系统是**显式代码编排的多 Agent 工作流**，而不是模型在同一上下文中无限自由选择工具。  
用户问题属于不可信文本，只作为 Prompt 数据传入；数据库操作采用只读策略。

## 二、系统架构

```text
                    ┌───────────────┐
                    │  用户问题     │
                    └──────┬────────┘
                           │
              ┌────────────▼──────────────┐
              │ SchemaCatalog             │
              │ 读取真实表/列/外键/样例    │
              └────────────┬──────────────┘
                           │
              ┌────────────▼──────────────┐
              │ TableSelectAgent          │
              │ Pydantic TableSelection  │
              │ + 表名合法性检查          │
              └────────────┬──────────────┘
                           │
              ┌────────────▼──────────────┐
              │ BFS complete_join_tables │
              │ 自动补全中间 JOIN 表      │
              └────────────┬──────────────┘
                           │
              ┌────────────▼──────────────┐
              │ SQLGeneratorAgent         │
              │ Pydantic SQLDraft        │
              └────────────┬──────────────┘
                           │
              ┌────────────▼──────────────┐
         ┌───►│ SQLValidator              │
         │    │ 安全门禁 + EXPLAIN        │
         │    └────────────┬──────────────┘
         │                 │
         │              校验通过
         │                 │
         │    ┌────────────▼──────────────┐
         │    │ SQLExecutor               │
         │    │ SQLite 只读查询           │
         │    └────────────┬──────────────┘
         │                 │
         │        有限次数错误反馈
         │                 │
         │    ┌────────────▼──────────────┐
         └────│ SQLRewriteAgent           │
              │ 根据错误码修复 SQL       │
              └───────────────────────────┘

                执行成功
                    │
          ┌─────────▼───────────────┐
          │ ResultSummaryAgent      │
          │ 引用真实数据生成中文答案│

          └─────────────────────────┘
```

> 重试次数耗尽时直接返回失败，不绕过安全门禁继续执行。

## 三、核心状态与数据契约

通过 Pydantic 约定各阶段结果：

- `TableSelection`：tables、reason、confidence、needs_clarification
- `SQLDraft`：sql、explanation、assumptions、cannot_fix
- `ValidationResult`：ok、code、message、normalized_sql
- `SQLAttempt`：sql、source、code、error（完整修复历史）
- `ExecutionResult`：columns、rows、row_count、truncated
- `FinalAnswer`：answer、evidence、caveats
- `WorkflowOutput`：sql、tables、answer、repair_attempts、error 等

因此 LLM 和数据库模块之间不依赖随意拼接的自然语言传递状态。

## 四、关键设计选择

### 4.1 解析数据库结构

使用 SQLAlchemy Inspector 与 MetaData 查询真实字段，获取行数、类型、非空、主键、值分布、样例及外键。将概要提供给选表 Agent，将详细 Schema 提供给生成与改写 Agent。

### 4.2 选表与 BFS 关联补全

选表 Agent 可能只选择 `customers` 与 `genres`，BFS 利用真实外键补全：

`customers → invoices → invoice_items → tracks → genres`

BFS 寻找结构最短路径，能减少遗漏中间表，但不能单独证明路径语义正确。对于多路径复杂数据库，应在生产级实现中增加歧义判定。

### 4.3 SQL 生成与校验

SQLGeneratorAgent 依据 Schema 写 SQLite SELECT；SQLiteValidator 在不运行原 SQL 的情况下使用 `EXPLAIN` 检查字段与编译语法。  
安全规则禁止 DELETE/UPDATE/DDL、多个语句；执行器进一步强制文件只读和 Authorizer。

### 4.4 SQL Rewrite

失败时将原 SQL、SQLite 错误码、真实 Schema、历史 SQL 交给 SQLRewriteAgent。
每次修复都重新检查；遇到安全拒绝立即停止；达到上限后给出错误状态。

### 4.5 执行与汇总

查询使用只读 SQLite 连接，设定最大行数、进度超时和单元格截断；
汇总 Agent 只根据真实 rows、SQL 与用户问题回答。
空结果直接报告“未查询到符合条件的数据”；汇总失败时降级为表格。

## 五、SQL 示例

**统计拥有 Rock 类型购买记录的不同客户数：**

```sql
SELECT COUNT(DISTINCT c.CustomerId) AS customer_count
FROM customers AS c
JOIN invoices AS i ON i.CustomerId = c.CustomerId
JOIN invoice_items AS ii ON ii.InvoiceId = i.InvoiceId
JOIN tracks AS t ON t.TrackId = ii.TrackId
JOIN genres AS g ON g.GenreId = t.GenreId
WHERE g.Name = 'Rock';
```

实际 Chinook 数据库结果为 **59 位客户**。结果可由 SQL 查询独立验证。

## 六、安全边界及改进方向

本项目的 SQLite 权限控制与超时限制适用于作业场景，但未实现完整生产沙箱。
SQL 编译成功不能保证业务语义正确，尤其是将外键 `GenreId` 错连 `MediaTypeId` 时。后续可引入 SQLGlot AST、JOIN 外键一致性检查、业务指标约束测试与数据库账号级隔离。

## 七、工程测试

单元测试通过 Monkeypatch 模拟 Agents SDK 的 `Runner.run`，不消耗模型 API 调用。  
系统接入真实模型之前，还应针对当前 SDK 版本与供应商的 JSON Schema/Responses 协议兼容性进行端到端验收。
