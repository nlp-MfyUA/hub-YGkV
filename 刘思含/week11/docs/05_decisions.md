# ChatBI-Vuln 项目 · 关键设计决策记录（Decision Log）

> **文档定位**：记录项目里"看似可优化、实际有理由"的设计选择。目的是防止 AI Coding 工具的**善意破坏**——看到某处可以做得更好，就顺手改了，不知道背后的权衡。
>
> **使用规则**：
> 1. Coding 工具在**修改任何架构级设计、数据结构、依赖选型**前，先查本文档。
> 2. 若改动的对象已有决策记录，**不得直接改**；必须先满足"推翻条件"或由项目负责人批准。
> 3. 新增决策时追加到文末，编号递增，不修改历史条目。

## D-001 · 解析层与 ChatBI 层完全解耦

- **决策**：解析层（Phase 2/3）产出的唯一对外接口是 `vuln.db`；ChatBI 层（Phase 4）只感知 `vuln.db`，不感知 PDF、不感知 `data/parsed_output/`、不感知 `data/images/` 的存在。
- **理由**：
  1. 解析是重操作（IO + OCR），ChatBI 是轻查询（SQL），两者运行时特性差异极大。耦合会导致"打开 ChatBI 就触发解析"的灾难。
  2. 解析失败不应影响 ChatBI 的可用性——已入库的数据仍能查，只是新报告还没进来。
  3. 解析器可能被替换（MinerU → pdfplumber），ChatBI 不应感知这个变化。
- **被否决的替代方案**：
  - 一体化：ChatBI 内部调用解析器"按需解析"。否决原因：每次对话都要检查是否需要解析，延迟不可控；解析失败会阻塞对话。
  - 共享内存：解析层与 ChatBI 运行在同一进程。否决原因：解析依赖的 PyTorch/OCR 会拖累 ChatBI 的启动时间和内存占用。
- **影响范围**：01 §0 关键原则 1、02 §10 模块依赖图、03 C-DEP-001~010
- **推翻条件**：报告数量极少（< 10 份）、解析耗时 < 5s、且需要"实时新增报告立即查询"的场景。
- **状态**：生效

## D-002 · 解析层不依赖 LLM

- **决策**：`pipeline/phase2_parse/` 与 `pipeline/phase3_load/` 禁止 import 任何 LLM SDK，禁止发起任何 HTTP 请求（本地部署的 OCR 引擎除外）。
- **理由**：
  1. 解析的可重复性要求高——同一份 PDF 两次解析应产出完全相同的结果。LLM 的温度参数和非确定性破坏了这一点。
  2. 渗透测试报告含敏感信息，不应外传。
  3. 字段映射、去重、归一化都是确定性规则问题，用 LLM 是杀鸡用牛刀，还引入不可控变量。
- **被否决的替代方案**：
  - 用 LLM 做字段映射（"从这段文字中提取漏洞名称"）。否决原因：准确率不稳定，无法审计，且表头映射用别名表完全够用。
  - 用 VLM 做图片语义描述。否决原因：见 D-004。
- **影响范围**：01 §0 关键原则 2、03 C-DEP-005、C-DEP-006
- **推翻条件**：报告格式完全无规律（表头每次都不同、漏洞描述是自由散文），且评测集证明规则法召回率 < 0.80。届时可考虑在解析层**外围**增加一个 LLM 辅助模块，但主链路仍保持确定性。
- **状态**：生效

## D-003 · 一切变更走增量

- **决策**：日常运行 `run_pipeline.py` 只处理变更文件，判定顺序为：索引不存在 → `pipeline_version` 不一致 → 内容哈希不一致 → 跳过。
- **理由**：
  1. 解析是重操作，全量重跑的成本随报告数量线性增长。
  2. 增量机制让"新增 1 份报告"的成本与"报告总数"无关。
  3. 幂等性：同一文件反复处理不产生重复数据。
- **被否决的替代方案**：
  - 按 `mtime` 判定变更。否决原因：读取、移动、权限变更等操作可能改变 `mtime` 但内容不变，导致误触发重跑。
  - 按文件名判定。否决原因：报告 v2 可能用同名文件替换 v1，文件名不变但内容变了。
- **影响范围**：01 §Phase 5、02 §8、03 C-VER-002、04 E-INC-001~006
- **推翻条件**：不推翻。增量是工程底线。
- **状态**：生效

## D-004 · MVP 不启用 VLM 图片语义描述

- **决策**：`ImageRecord.generated_description` 恒为 `None`；`corpus_profile.image_strategy.vlm_description_enabled` 必须为 `false`，为 `true` 时启动即抛异常。
- **理由**：
  1. VLM 存在"文本先验压倒视觉证据"的幻觉倾向——模型可能基于上下文"编造"图片内容，而不是忠实描述像素。
  2. 漏洞细节的可信度要求极高。回答"payload 是什么"时，编造一个 payload 比"未找到"更危险。
  3. OCR 已能覆盖 80% 的细节问答需求（payload、请求路径、报错文本），VLM 的边际收益不足以对冲幻觉风险。
- **被否决的替代方案**：
  - MinerU 的 vlm 后端。否决原因：同 1/2。
  - 云端多模态 API。否决原因：报告敏感信息不外传（C-SEC-001）。
- **影响范围**：01 §Phase 2、02 §1.2、03 C-IMG-001、C-CTR-005
- **推翻条件**：评测集新增 5 条 VLM 描述用例，与人工标注的一致率 ≥ 90%，且不引入新的隐私风险。届时可重新评估。
- **状态**：生效

## D-005 · 图片不存 BLOB 存文件路径

- **决策**：图片文件落盘到 `data/images/{pdf_stem}/{page}_{idx}.png`；SQLite 的 `v_image_evidence` 只存相对路径 `image_path`。
- **理由**：
  1. SQLite 存大 BLOB 会显著膨胀数据库文件，影响查询性能。
  2. 图片需要被前端直接加载展示，文件系统更自然。
  3. 备份、迁移、清理图片可以独立于数据库进行。
- **被否决的替代方案**：
  - 存 BLOB。否决原因：单库可能达数 GB，备份与 WAL 写入性能下降。
  - 存 base64 字符串。否决原因：比 BLOB 还大 33%，且 SQLite 的 TEXT 存储效率不如 BLOB。
- **影响范围**：01 §1 目录结构、02 §1.2、03 C-IMG-002、C-IMG-003
- **推翻条件**：不推翻。这是 SQLite 场景的标准做法。
- **状态**：生效

## D-006 · 单 Agent + 五工具，不做 Handoff

- **决策**：ChatBI 层用一个 Agent，挂五个 Function tools（`get_schema`、`search_knowledge`、`execute_sql`、`search_image_evidence`、`render_chart`），不做多 Agent 的 Handoff。
- **理由**：
  1. 问数场景的任务路径是线性的：理解 → 查 schema/知识库 → 生成 SQL → 执行 → 展示。不需要"路由到不同专家 Agent"。
  2. 知识库优先/生成兜底的路由逻辑在 Python 工具内部判断比让 LLM 判断更稳定。
  3. 多 Agent 增加调试面、延迟和 token 消耗，对 MVP 场景收益有限。
- **被否决的替代方案**：
  - Planner + Executor + Reviewer 三 Agent 链。否决原因：延迟翻倍，且 MVP 场景下 Reviewer 的能力不足以发现 Executor 的错误。
  - 按问题类型 Handoff（统计问题→统计 Agent，细节问题→细节 Agent）。否决原因：路由本身需要 LLM 判断，不确定性反而增加。
- **影响范围**：01 §Phase 4、02 §7.1
- **推翻条件**：出现多类明显异构的查询需求（例如同时要查数据库、查文档、调用外部 API），且各自需要专门的工具集与指令。届时可拆分为 2–3 个 Agent。
- **状态**：生效

## D-007 · `component=None` 入库前转空字符串

- **决策**：入库前将 `CanonicalVulnRecord.component` 的 `None` 统一转为 `""`，再走 UPSERT。
- **理由**：
  1. SQLite 的 `ON CONFLICT` 不支持直接引用表达式索引（`COALESCE(component, '')`），必须用列名。
  2. 方案 B（入库前转换）比方案 A（用生成列）实现简单，无需修改 schema 迁移。
  3. `component` 为空字符串与 `component` 为 `NULL` 在本场景中语义等价（都是"未指定组件"）。
- **被否决的替代方案**：
  - 方案 A：增加 `component_key TEXT GENERATED ALWAYS AS (COALESCE(component,'')) VIRTUAL`，唯一索引建在 `(source_file, vuln_name, component_key)` 上。否决原因：MVP 不需要 NULL 语义，增加复杂度。
  - 完全不建唯一索引，靠业务层去重。否决原因：业务层去重易被绕过，无法防止并发重跑造成的重复。
- **影响范围**：02 §6.3、03 C-CTR-007、06 SQLite 陷阱条
- **推翻条件**：需要区分"组件未指定"（`NULL`）与"组件是空字符串"（`""`）的业务语义。届时迁移到方案 A。
- **状态**：生效

## D-008 · FTS5 用 trigram 分词器

- **决策**：`v_image_evidence_fts` 使用 `tokenize='trigram'`，而不是默认的 `unicode61`。
- **理由**：
  1. 渗透报告截图中的文本是中英文混合（如 "SQL Injection 漏洞，payload 为 `' OR 1=1--`"），`unicode61` 对中文只能按单字切分，检索效果差。
  2. `trigram` 支持子串匹配（任意 ≥ 3 字符的连续片段都能命中），对 payload、URL 这类碎片化文本的检索更友好。
  3. 对中英文混排的模糊匹配准确率显著优于 `unicode61`。
- **被否决的替代方案**：
  - `unicode61`。否决原因：中文切分粒度太细，检索召回过低。
  - 外部中文分词插件（如 `simple` 或自定义 tokenizer）。否决原因：SQLite 编译期依赖，不同环境不一致。
  - 用 `LIKE` 代替 FTS5。否决原因：无法做相关性排序，且全表扫描性能差。
- **影响范围**：02 §2 schema、06 FTS5 陷阱条
- **推翻条件**：SQLite 版本 < 3.34（`trigram` 不可用）。届时降级到 `unicode61`，并把评测集的中文用例占比调低，接受召回损失。
- **状态**：生效

## D-009 · `search_image_evidence` 不暴露 FTS 表

- **决策**：`v_image_evidence_fts` 不加入 `execute_sql` 的表名白名单；Agent 只能通过 `search_image_evidence` 工具访问 FTS 表。
- **理由**：
  1. FTS5 的 `MATCH` 语法允许用户传入特殊字符（`"` `*` `(` `NEAR` 等），直接暴露给 LLM 生成的 SQL 有语法注入风险。
  2. `search_image_evidence` 内部可以做关键词转义、结果截断、不可信内容标注、限额控制，这些逻辑放在工具内部比放在 Agent instructions 里更可靠。
  3. 保持 `execute_sql` 白名单的稳定性和最小化。
- **被否决的替代方案**：
  - 把 FTS 表加入白名单，让 Agent 直接 `SELECT ... FROM v_image_evidence_fts WHERE ...`。否决原因：特殊字符转义、注入防护、结果截断都必须在 SQL 生成层面保证，不可靠。
- **影响范围**：02 §7.2.3、§7.2.4、03 C-RO-006、C-RO-007
- **推翻条件**：不推翻。
- **状态**：生效

## D-010 · 图片与漏洞关联用页码邻近启发式

- **决策**：`ImageRecord.linked_vuln_name` 通过"图片所在页 ± `link_page_window` 页内的漏洞记录"来关联；多个候选时取页差最小者。
- **理由**：
  1. 渗透报告的典型排版是"漏洞描述 + 紧跟 POC 截图"，页码邻近是最可靠的低成本信号。
  2. 不依赖图片内容理解（那需要 VLM，见 D-004）。
  3. 关联失败时（`linked_vuln_name=None`）不影响图片入库，仍可通过全库 FTS 检索到。
- **被否决的替代方案**：
  - 用图片位置与漏洞所在 bbox 的距离关联。否决原因：pdfplumber 与 MinerU 的 bbox 坐标系不一致，增加实现复杂度。
  - 用表头关键词命中图片附近的文本。否决原因：图片附近常有"图 3.1 SQL 注入验证"这类标题，但标题的可靠性不如页码直接。
- **影响范围**：02 §5.7、03 C-IMG-007、04 E-PARSE-007
- **推翻条件**：`E-PARSE-007`（图片关联率）在优化后仍 < 0.60，说明页码邻近失效，需要引入基于文本的关联策略。
- **状态**：生效

## D-011 · OCR 原文不清洗后入库

- **决策**：`ImageRecord.ocr_text` 存 OCR 引擎的**原始输出**，不做任何清洗（不去空格、不修 URL、不做字符替换）。清洗只在 FTS 检索时进行。
- **理由**：
  1. 可审计：人工复核时可以对照原始 OCR 输出与清洗后文本，定位识别误差来源。
  2. 可重跑：清洗规则变更时不需要重新 OCR（OCR 慢，清洗快）。
  3. 不同场景需要不同清洗：入库时不知道下游会怎么用 OCR 文本，保守存原文。
- **被否决的替代方案**：
  - 入库时清洗（去空格、拼接 URL、规范化标点）。否决原因：清洗规则一旦有误，错误会在数据层固化，且不可逆。
- **影响范围**：02 §1.2、§5.7、03 C-IMG-006、C-CTR-004
- **推翻条件**：不推翻。这是数据处理的标准分层原则。
- **状态**：生效

## D-012 · 门禁线不可豁免，良好线可记债

- **决策**：04 §7 定义的门禁线指标（如 E-PARSE-001 ≥ 0.85）**不可通过任何流程豁免**；未达良好线可记入 `docs/tech_debt.md`，30 天内修复。
- **理由**：
  1. 门禁线是项目对质量的**最低承诺**。一旦可豁免，门禁形同虚设。
  2. 良好线是**优化目标**，允许"先过线后修复"的渐进式质量提升。
  3. 这一区分避免"每次都能想办法豁免"的滑坡效应。
- **被否决的替代方案**：
  - 门禁线也可豁免（需项目负责人批准）。否决原因：时间压力下会滥用，导致低质量代码进入主分支。
- **影响范围**：04 §7、§9、03 §11.3
- **推翻条件**：不推翻。
- **状态**：生效

## D-013 · 知识库优先，生成兜底

- **决策**：ChatBI 收到问题后，先调 `search_knowledge` 查 `kb_entry` 中已审核的模板；命中则直接执行模板 SQL；未命中才调 `get_schema` 并生成 SQL。
- **理由**：
  1. 高频问题的正确率是用户最敏感的指标。模板命中保证 100% 正确。
  2. 生成路径的准确率受 LLM 能力与 Schema 复杂度影响，不稳定。
  3. 知识库积累后，后续新用户的高频问题都能命中，减少对 LLM 的依赖。
- **被否决的替代方案**：
  - 全部生成，知识库仅作提示。否决原因：正确率下降，用户体验不稳。
  - 全部查表，不生成。否决原因：无法覆盖长尾问题。
- **影响范围**：01 §Phase 4、02 §7.2.2、§7.2.3
- **推翻条件**：`kb_entry` 的维护成本超过收益，且 LLM 生成的正确率稳定 ≥ 95%。
- **状态**：生效

## D-014 · 增量判定顺序固定

- **决策**：`ProcessingPlan` 的判定顺序固定为：① 索引不存在 → ② `pipeline_version` 不一致 → ③ 内容哈希不一致 → ④ 索引存在但文件消失 → ⑤ 全部一致则跳过。
- **理由**：
  1. `pipeline_version` 的判定**优先于**内容哈希，是为了保证"配置变更时所有文件都重跑"，即使文件本身没变。
  2. 文件消失的判定放在最后，避免误删（文件暂时不可读时不标记为 orphan）。
  3. 顺序固定后，调试时日志里的 `reason` 可以直接反映根因。
- **被否决的替代方案**：
  - 先查哈希再查版本。否决原因：配置变更时大量文件哈希计算是浪费，先查版本能快速过滤。
- **影响范围**：01 §Phase 5、02 §8.2、03 C-VER-002
- **推翻条件**：不推翻。
- **状态**：生效

## D-015 · 孤儿软删除，延迟物理删除

- **决策**：文件从 `deliverables/` 消失时（按 `relative_path` 对账，而非仅文件名），相关记录标记为 `status='orphaned'`，不立即物理删除。若后续多次对账该文件仍不存在，才在独立的 `cleanup_orphans()` 中物理删除。
- **理由**：
  1. 文件系统挂载问题、权限变更、网络抖动都可能导致文件"暂时消失"，直接物理删除会造成不可恢复的数据丢失。
  2. 软删除保留了审计痕迹，可以追溯"某份报告何时被移出"。
  3. 物理删除作为独立步骤，可以按需执行（如季度清理），不阻塞日常流程。
- **被否决的替代方案**：
  - 立即物理删除。否决原因：风险高。
  - 永不删除。否决原因：数据库无限增长，且 `v_image_evidence` 的孤儿记录会占据 FTS 索引空间。
- **影响范围**：01 §Phase 5、02 §8.3
- **推翻条件**：不推翻。
- **状态**：生效

## D-016 · Phase 2 以文本切分为主路径，表格仅作辅助

- **决策**：Phase 2 处理链路改为 `Adapter → 目录页剔除 → 文本块切分（TextBlockLocator） → 字段提取（FieldExtractor） → 表格辅助（仅附录/摘要校验）`。漏洞记录只从文本块产生；表格仅用于附录风险等级定义（`v_type_catalog` 初始化参考）与摘要计数校验，不作为漏洞记录来源。
- **理由**：
  1. Phase 1 勘察 8 份真实样本，pdfplumber 共识别 11 个表格对象，**0 个漏洞详情表**；其中 8 个是附录「风险等级定义表」，3 个是同一附录表跨页续行（slot 2 p5、slot 3 p54、slot 4 p19）。
  2. 漏洞详情实际是文本结构：渗透为 `N．名称（等级）` + `（1）漏洞描述` / `（2）漏洞位置` / `（3）测试过程` / `（4）整改建议`；回归为 `（一）名称` + `漏洞描述：` / `漏洞位置：`，并存在 `（二十）` 与“标签独占一行”变体。
  3. 表格 Locator 在真实语料上无召回；若继续以表格为主路径，363 份报告会几乎全部被判为 `fail`。
  4. 文本切分可行性已验证：8 份中 7 份的条目数与摘要一致；唯一不一致是 slot 1 的源数据问题（摘要 5 vs 目录/正文 2）。
- **被否决的替代方案**：MinerU 表格优先。否决原因：MinerU 也不会把“标题 + 描述段落 + 截图”恢复为规则表格；换 Adapter 只增加模型下载与运行成本，不能解决结构问题。
- **影响范围**：02 §5.4–5.6、§5.9、§11；03 C-NAM-008 / C-CTR-012 的中间产物名与 `extraction_method` 枚举需同步；04 E-PARSE-005 的 `count_cross_check` 继续适用。
- **推翻条件**：若后续真实语料中 ≥30% 报告的漏洞详情以规则表格呈现，可重新评估表格 Locator 作为补充路径。
- **状态**：生效（Phase 2 设计依据；`corpus_profile.json` 仍待 H-02 批准）

## D-017 · 回归报告用 v_retest_result 表建模，不写入 v_vulnerability

- **决策**：回归报告产出 `RetestRecord`，指向 `v_vulnerability` 的 `vuln_id`；不新增漏洞记录。
- **理由**：回归报告是复测记录，不是独立漏洞来源；若写入 `v_vulnerability` 会导致 ChatBI 统计重复计数。
- **被否决的替代方案**：
  - 方案 A（在 `v_vulnerability` 加 `retest_status` 字段）：不支持多次复测。
  - 方案 C（回归报告只存摘要）：丢失逐条复测信息，无法回答“哪些高危未修复”。
- **影响范围**：`schema.sql`、02 §1/§2/§5.5/§6/§7、03 C-RO-005、04 的 E-LOAD 指标。
- **推翻条件**：匹配率持续低于 50%，方案 B 的 `vuln_id` 大量为空，复测信息价值低于维护成本。
- **状态**：生效（schema 更新在方案 B 第二段执行）
- **补充决策**：无漏洞的渗透报告（49 份）不产出 `v_vulnerability` 记录，在 `pdf_index` 中标记 `parse_status='no_vulnerabilities'`。ChatBI 回答“未修复”类问题时只需报“已修复”和“未修复”两个数字，不需要提“未复测”。

## D-018 · retest 匹配采用 parent_vuln_name + component 严格匹配

- **决策**：`v_retest_result.vuln_id` 的匹配条件为 `report_id = parent_report_id AND vuln_name = ? AND COALESCE(component,'') = ?`。
- **理由**：Phase 1 勘察时按名称匹配 87/87；`component` 参与匹配可避免同名不同位置的漏洞误配。
- **风险**：若渗透报告的 `component` 非空而回归报告为空，同名漏洞会判为不匹配。
- **验证结果**：slot 6 `matched=27/27（100%）`，`unmatched=0`。注：父渗透报告 27 条 canonical 记录因 `component` 为空，在 `v_vulnerability` 中收敛为 20 行（7 次 update），同名重复漏洞共享 `vuln_id`；匹配计数仍为 27/27。该 27→20 收敛问题已由 D-019 的 instance_index 修复。
- **推翻条件**：若真实数据 `matched < 90%`，改为“名称匹配 + component 辅助评分”（`match_confidence='exact'` 或 `'fuzzy'`）。
- **状态**：生效（匹配率验证后更新）

## D-019 · v_vulnerability / v_retest_result 增加 instance_index，唯一键扩展为四列

- **决策**：同名漏洞不合并入库，靠 `instance_index` 区分；retest 匹配靠 `(名称, component, instance_index)` 三条件配对。
- **理由**：Phase 3 真实数据验证发现渗透报告 27 条记录收敛为 20 行（3 个“前端校验绕过”合并），丢失 7 条记录的详情；ChatBI 无法区分“第几个前端校验绕过”。
- **被否决的替代方案**：方案 B（occurrence_count 计数），统计正确但丢失逐条详情，无法回答“第 2 个前端校验绕过的截图”。
- **影响范围**：`CanonicalVulnRecord`、`RetestRecord`、`v_vulnerability`、`v_retest_result`、`field_extractor`、`sqlite_loader`、`retest_loader`、所有测试 fixture。
- **已知限制**：`v_image_evidence.linked_vuln_name` 只存名称，不区分 `instance_index`；同名漏洞的图片无法精确归到某个实例。
- **推翻条件**：不推翻。
- **状态**：生效
