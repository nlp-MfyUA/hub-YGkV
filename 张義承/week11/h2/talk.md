## 背景澄清：ChatBI vs Data Agent

### ChatBI —— 自然语言问数

把 BI 的"取数 + 出图"换成对话：自然语言提问 → NL2SQL → 查库 → 表格/图表。

```
"上个月华东区销售额是多少？" → NL2SQL → 查询 → 图表
```

核心能力三件事：**意图理解、NL2SQL、结果可视化**。
隐藏前提：需要语义层/指标口径治理，否则同一个"销售额"会问出多个数。

典型场景：
- 业务人员自助取数，不再排队等数据分析师
- 管理者手机问数：日报、周报、指标异动
- 客服/运营查订单、库存、履约状态
- 替代固定报表中的"下钻"操作

代表产品：Quick BI 智能问数、网易有数、Power BI Copilot、Tableau Pulse。

### Data Agent —— 能独立完成一整件数据工作

以 LLM 为大脑，带一组工具（SQL、Python、检索、文件读写），自主规划步骤、执行、看结果、自我纠错，端到端交付任务。

```
"分析本季度转化率下滑原因，出份报告"
  → 拆解：取数 → 多维对比 → 归因 → 画图 → 写结论
  → 中途发现字段缺失 → 换数据源重试
```

### 两者区别

| | ChatBI | Data Agent |
|---|---|---|
| 交互 | 一问一答 | 给目标，自己规划 |
| 步骤 | 单步（问数） | 多步、可回退 |
| 工具 | SQL + 图表 | SQL、Python、检索、文件、API |
| 交付物 | 一个数字/一张图 | 报告、分析结论、清洗后的数据集 |
| 出错 | 答错就答错 | 会自查、重试、换路径 |

**一句话**：ChatBI 是"问数的界面"，Data Agent 是"能干活的实习生"。常见演进路径是先做 ChatBI，再叠加工具调用与规划能力升级为 Data Agent。

## ChatBI 能力地图

### 6 个能力域

1. **数据接入与语义层**
   - 连接数据库，抽取 schema（表、字段、类型、主外键）
   - 表/字段的人话描述与同义词（`cust_id` ← 客户/用户/客户编号）
   - 指标口径定义（销售额、活跃用户、转化率的算法）
   - 表多时需要先检索"该用哪几张表"，而非全量塞入 schema
2. **自然语言理解**
   - 意图识别（问数 / 闲聊 / 作图 / 导出）
   - 实体抽取（指标、维度、筛选、聚合方式）
   - 时间消解（"上个月""最近一周" → 具体日期区间）
   - 歧义消歧（"销售额"是下单金额还是实付金额）
   - 多轮上下文（"那华东呢？"继承上句条件）
3. **NL2SQL**
   - 方言适配（SQLite / MySQL / PostgreSQL）
   - join、group by、TopN、同环比、窗口函数
   - few-shot 示例提升稳定性
   - 只读约束，拦截 INSERT/UPDATE/DELETE/DDL
   - LIMIT 与超时防护
4. **执行与容错**
   - 捕获报错并回传给模型重写（收益最明显的自修复）
   - 空结果判断：业务真无数据 vs SQL 写错
   - 结果规模与耗时控制
5. **结果呈现**
   - 单值 → 指标卡；时间序列 → 折线；分类对比 → 柱状；占比 → 饼图（≤6 类）
   - 自动生成图表配置 + 自然语言结论
   - 始终展示生成的 SQL，建立可信度
6. **安全、会话与治理**
   - 行级/列级权限、敏感字段脱敏
   - 审计日志（谁、何时、问了什么、查了什么）
   - 多轮会话管理、历史记录、澄清反问
   - 评测：问数准确率、执行成功率、图表选型正确率

### 优先级分层

| 层级 | 能力 | 说明 |
|---|---|---|
| **P0 必须** | 数据接入 → 意图理解 → NL2SQL → 执行 → 表格展示 → 展示 SQL | 缺了不叫 ChatBI |
| **P1 该有** | 图表自动选型、报错自修复、时间消解、多轮上下文、澄清反问 | 决定可用性与体验 |
| **P2 加分** | 语义层/指标口径、schema 检索、权限脱敏、评测集、缓存 | 决定能否上线 |

**课程作业取舍建议**：P0 + 挑 2～3 项 P1；P2 中挑一项讲清设计取舍，报告分量即够。

### 已知的高频坑

1. 口径歧义——模型不知道"销售额"的定义
2. 时间理解——"上个月"是自然月还是过去 30 天
3. join 关系——多表时模型自编外键，结果数量级错误
4. 空结果——直接答"没有数据"，无法区分业务无数据与 SQL 错误
5. 图表选错——12 个类别塞饼图、时间趋势画柱状

## Python 开发所需技能

**判断**：Python 本身是最不重要的技能；SQL、数据理解、提示词/上下文设计才是决定成败的部分。

### 技能清单

| 能力域 | Python 相关技能 | 必备度 |
|---|---|---|
| 数据库 | 扎实 SQL（join、group by、子查询、窗口函数）、`sqlite3`/`SQLAlchemy`、schema 内省 | ★★★ |
| 数据处理 | `pandas`、JSON 序列化、类型转换 | ★★★ |
| LLM 接入 | API 调用、流式输出、超时重试、token 成本 | ★★★ |
| 提示词工程 | schema 上下文组织、few-shot、输出格式约束 | ★★★ |
| 结构化输出 | JSON Schema / Pydantic 校验、解析失败降级 | ★★☆ |
| 界面 | `Streamlit`（推荐）或 `FastAPI`；会话状态管理 | ★★☆ |
| 可视化 | `Plotly`/`Altair`、图表选型 | ★★☆ |
| 工程化 | 模块拆分、异常处理、日志、`.env`、`pytest`、依赖锁定 | ★★☆ |
| 安全 | 只读连接、SQL 关键字拦截、输入校验 | ★★☆ |
| 异步/并发 | `async/await` | ★☆☆（Streamlit 场景可不用） |

### 不能外包给 AI 的最小集

1. 能看懂并改写 SQL（尤其识别 join 少条件导致的数据翻倍）
2. 能描述数据：表/字段含义与指标口径
3. 能设计提示词结构：系统提示、示例、输出约束
4. 能定位报错来源（SQL / API / 界面），并准确反馈给 AI

### vibe coding 分工

| 角色 | 负责方 |
|---|---|
| 需求边界、验收标准 | 用户 |
| 数据理解、口径定义、SQL 正确性判断 | 用户 |
| 写代码、搭界面、调参数 | AI |
| 运行、观察、发现问题并反馈 | 用户 |
| 代码审查与重构 | AI，用户抽查关键逻辑 |

**结论**：用户的技能重点在"能验收"，而非"能默写"。

### 补课优先级

SQL（join/聚合）→ LLM API 与结构化输出 → Streamlit → pandas → 工程化

## 如何理解"面向什么数据"

拆成三个问题：**结构、业务、难度**。

### 1. 结构（数据长什么样）

- 有几张表：单表 / 两三张 / 十几张
- 一行代表什么：一条订单 / 一个客户 / 一次工单
- 度量：能 sum/avg 的数字（金额、数量、时长）
- 维度：能分组的字段（地区、品类、渠道、状态）
- 表关系：外键、1:N 还是 N:N
- 时间字段的粒度（有下单时间、支付时间时取哪个）

单表项目无需 join，难度低一档；多表项目 join 易错，但最能体现完整度。

### 2. 业务（能回答什么问题）

| 数据域 | 典型问题 | 难点 |
|---|---|---|
| 电商销售 | 上月华东 GMV？哪个品类增速最快？ | 口径多、时间对比 |
| 客服工单 | 本周投诉量？平均响应时长？ | 时长指标、状态流转 |
| 库存供应链 | 哪些 SKU 缺货？周转天数？ | 快照表、时点计算 |
| 财务 | 本月毛利率？费用同比？ | 口径严谨、层级汇总 |
| 用户增长 | 新老客占比？次月留存？ | 生命周期定义 |

**这些问题就是验收用例。** 数据选错，问题就长不出来。

### 3. 难度

| 维度 | 简单 | 困难 |
|---|---|---|
| 表关系 | 单表 | 多表 join / 星型模型 |
| 时间 | 单一时点 | 同环比、自然月 vs 滚动窗口 |
| 维度 | 低基数分类 | 多级层级（国家→省→市） |
| 数据量 | <1 万行 | 百万行 |
| 字段名 | `product_name` | `prod_nm_cn`、`flag_a` |

### 选数据的 5 条标准

1. 用户熟悉业务，能判断答案对错
2. 3～6 张表，关系清晰
3. 同时有时间和类别维度
4. 本地可跑（几万～几十万行，SQLite 足够）
5. 字段名与业务语言对得上

### 候选数据集

| 数据集 | 表数 | 优点 | 缺点 |
|---|---|---|---|
| **自建电商销售库（倾向）** | 4～5 | 口径可控、业务好懂、问题好出 | 需自己造数 |
| Northwind 北风 | 8 | 经典、关系完整、真实感强 | 表偏多，易混淆 |
| Superstore | 1（宽表） | 开箱即用、字段干净 | 单表，练不到 join |
| TPC-H | 8 | 工业级、规模可调 | 偏基准测试，业务感弱 |
| Chinook | 11 | 现成 SQLite 文件 | 音乐商店偏冷门，问题类型少 |

**倾向：自建 4～5 张表的电商销售库**；最省事的替代是 Northwind。

### 判断是否真的理解了数据

动手前需能回答：
1. 这张表一行代表什么？
2. 哪些字段可加总，哪些只能计数？
3. 两张表靠哪个字段连接？
4. "上个月"取哪个时间字段？

## 数据方案：自建电商销售库（已定）

用途：学习使用。设计目标是覆盖 ChatBI 典型考点，并让每张表都承载一个教学点。

### 表结构（5 表）

```
customers ──1:N──> orders ──1:N──> order_items <──N:1── products
                      │
                      └──1:N──> refunds
```

**customers**：customer_id、customer_name、gender、birth_date、province、city、register_date、member_level
- 教学点：维度表；会员分层、新老客户分析

**products**：product_id、product_name、category、sub_category、brand、list_price、cost_price
- 教学点：多级维度下钻；成本价可算毛利

**orders**：order_id、customer_id、order_date、pay_date、status、channel、shipping_province、pay_amount、discount_amount
- 教学点：两个时间字段 → 时间口径；status → 销售额是否含取消订单

**order_items**：item_id、order_id、product_id、quantity、unit_price、item_amount
- 教学点：拆解 orders↔products 多对多；商品维度分析必经此表

**refunds**：refund_id、order_id、refund_date、refund_amount、reason
- 教学点：指标口径第二层（销售额是否减退款、退款率定义）

### 指标口径（必须提前定死）

| 指标 | 定义 |
|---|---|
| 有效订单 | status ∈ {已支付, 已发货, 已完成} |
| GMV / 销售额 | 有效订单 pay_amount 之和（默认含退款） |
| 净销售额 | GMV − 退款金额 |
| 客单价 | 销售额 ÷ 下单客户数 |
| 退款率 | 退款金额 ÷ GMV |
| 复购率 | 购买 ≥2 次的客户 ÷ 有购买记录的客户 |

**默认约定**：问"销售额"一律指 GMV；问"退款"时才引入 refunds 表。

### 验收用例（20 问）

- 单值：上月销售额、本月有效订单数
- 趋势：近 12 个月销售额走势、各月订单量
- 排名：销售额 Top10 商品、各品类销售额、各省份销售额
- 占比：各渠道销售额占比、各会员等级客户数占比
- 时间对比：本月 vs 上月增速、今年 vs 去年双 11
- 比率：客单价、退款率最高品类、复购率
- 下钻：数码品类下各子类目销售额
- 关联：金卡会员平均消费、A 品类客户的第二常购品类、各注册年份客户贡献
- 明细：本月金额 Top20 订单、某客户全部订单

### 数据规模

| 项 | 规模 |
|---|---|
| 客户 | 1,000 |
| 商品 | 200（8 个一级类目） |
| 订单 | 10,000（跨度 2 年） |
| 明细 | ~30,000 |
| 退款 | 500（约 5%） |

**造数需埋入的业务规律**：双 11/618 峰值；金卡客单价与复购更高；品类季节性；少数爆款销量集中。

### 取舍

- 5 表而非 3 表：保留退款表才能讨论指标口径，这是 ChatBI 最有含金量的部分
- 加 pay_date：制造真实的时间口径歧义
- 可砍：refunds 可删，降为 4 表、仅保留 GMV

## 2026-10-21 · 框架确定（不写实现代码）

**本轮范围**：只搭框架，不写任何实现代码。

**产出**：`框架设计.md`

**框架包含的 6 件事**

1. **分层架构**：表现层 UI → 应用层 Orchestrator → 智能层 → 数据层 → 基础设施；依赖单向向下
2. **主流程**：意图识别 → 槽位检查 → 上下文组装 → NL2SQL → 安全校验 → 执行 → 自修复 → 空结果判断 → 图表选型 → 摘要 → 返回
3. **模块职责表**：12 个模块的输入、输出、失败策略
4. **接口契约**：ChatRequest / SessionContext / IntentResult / PromptContext / SQLPlan / ExecutionResult / ChartSpec / ChatAnswer
5. **目录结构**：config / core / data / guard / llm / ui / models / infra / eval / scripts / tests
6. **里程碑**：M0 数据就绪 → M1 单表问数 → M2 多表与口径 → M3 容错与呈现 → M4 多轮澄清 → M5 评测打磨

**关键设计决策**

- 失败是一等公民：澄清、安全拒绝、自修复耗尽都是正常状态，不抛异常穿透到 UI
- 智能层与数据层解耦：智能层只拿 schema 元数据，不直接连库
- 语义层独立于代码，用 YAML 维护（表描述、同义词、指标口径、时间规则）
- 提示词四层：角色规则 → 数据上下文 → 口径与示例 → 本轮问题
- 建议档位：M0～M3 必做，M4 视时间，M5 用于报告

## 2026-10-21 · 验收标准（用户给定，最高优先级）

功能可以少，以下两条不能破。

### A. 数据不编造、全可追溯

- 回答中的一切数据必须来自数据库查询，模型不得编造
- 日志须记录数据来源（库/表/字段）与完整 SQL
- 查不到就说查不到，不给猜测值

**验证方式**：摘要中每个数字都能在结果集中找到；问一个库里没有的指标，系统必须如实说"查不到"。

### B. 隐私安全与鉴权（用户修正）

**用户指出的关键问题**：仅对姓名脱敏但返回其购买记录，仍然构成隐私泄露。因此不能"默认脱敏"，而要"默认拒绝"。

- 默认只允许聚合查询；涉及具体客户/账号的个体查询默认拒绝
- 仅当请求者具备权限（customer 查本人 / admin 查明细）时才可执行，且结果仍脱敏
- 无权限或目标不存在，统一回复：「该用户不存在，或您无权查询该用户的记录。」
- 两种情况的返回内容、结构、响应时间必须一致，防止账号枚举
- 权限相关查询必须审计：请求者账号、角色、行为、时间、目标主体（哈希）、决策

**验证方式**：
- 分析师问"客户张三买了什么" → 统一拒绝话术，不返回任何订单数据
- 问一个不存在的客户 → 返回完全一致的话术，不可区分
- 审计日志含账号、行为、时间；日志与审计中搜不到完整姓名

### 角色矩阵

| 角色 | 聚合查询 | 个体明细 | 说明 |
|---|---|---|---|
| analyst 分析师 | 允许 | 拒绝 | 只能看统计 |
| customer 客户 | 允许 | 仅本人 | 账号绑定 customer_id，结果仍脱敏 |
| admin 管理员 | 允许 | 允许 | 展示仍脱敏，全程审计 |

### 待确认的歧义

"不允许造数据"可能是：
- **A 读法**：只约束系统回答不得编造（示例数据仍可由脚本生成）——框架暂按此设计
- **B 读法**：连数据准备也不许脚本生成，必须使用真实数据源——若是此读法，需重新选数据源

### 对框架的影响

- 主流程：会话认证 → 权限预检（NL2SQL 之前）→ 客体校验（执行前）→ 溯源 → 脱敏
- 新增模块：`guard/auth`（认证与权限）、`guard/privacy`（脱敏）、`infra/provenance`（溯源）、`infra/audit`（审计）
- 新增契约：`Principal`、`AuthDecision`、`ProvenanceRecord`、`AuditRecord`
- 两级校验：主体预检（聚合/个体）+ 客体校验（表白名单/禁用字段）
- 里程碑调整：M4 改为"隐私、鉴权与审计"，M0～M4 为必做
- 防侧信道：拒绝路径不查库，返回与"不存在"完全一致

| 5 | 技术选型 | 模型与 API、图表库、DB 形态 |
| 6 | 交互与失败态 | 澄清话术、错误提示、SQL 展示方式 |
| 7 | 排期与交付物 | M0～M5 任务拆分 |

### 为什么验收集排第一

- 验证数据是否够用：写不出正确 SQL 说明设计有问题
- 锁定口径：口径写在 SQL 里比写在文档里硬
- 提供 few-shot 素材：最准确的示例就是这批问答对
- 提供评测基线：改提示词后跑一遍即知效果

**vibe coding 关键**：先定义可验证的目标，再让 AI 实现。

### 验收规格模板（五要素）

1. 用户原话
2. 涉及表
3. 口径（指标定义 + 时间字段）
4. 正确 SQL（文字描述）
5. 期望结果（行数、列名、图表类型）

### 暂不讨论

UI 布局配色、部署与并发、权限脱敏（P2），待主流程跑通再谈。
