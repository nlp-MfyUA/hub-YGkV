## 2. 技术选型

### 2.1 选型清单

| 类别 | 选型 | 版本建议 | 理由 |
|---|---|---|---|
| 语言 | Python | 3.11+ | 生态成熟，LLM 与数据工具齐全 |
| 界面 | Streamlit | 1.36+ | 单文件即可出对话界面，迭代最快 |
| 数据库 | SQLite | 3.40+ | 单文件、零配置、只读连接简单 |
| DB 驱动 | `sqlite3`（标准库） | — | 无额外依赖，满足只读查询 |
| SQL 解析 | `sqlglot` | 25+ | 能区分语句类型、提取表/列，支持 SQLite 方言 |
| 数据校验 | Pydantic | 2.7+ | 边界契约与 LLM 输出校验 |
| 配置 | `pydantic-settings` + PyYAML | 2.x / 6.x | 环境变量与 YAML 统一校验 |
| 提示词模板 | Jinja2 | 3.1+ | 条件、循环、变量替换 |
| LLM SDK | `openai` | 1.30+ | 兼容 OpenAI 协议的供应商可直接使用 |
| 图表 | Plotly | 5.20+ | 与 Streamlit 集成好，图表配置可序列化 |
| 密码哈希 | `argon2-cffi` | 23+ | 抗暴力破解，API 简单 |
| 测试 | pytest + pytest-cov | 8.x / 5.x | 标准组合 |
| 静态检查 | ruff + mypy | 最新 | 快、规则全 |
| 依赖管理 | uv | 最新 | 锁定快，安装快 |

### 2.2 关键取舍

| 备选 | 是否采用 | 原因 |
|---|---|---|
| FastAPI + 前端 | 否 | 前后端分离增加联调成本，本项目单机演示无收益 |
| SQLAlchemy | 否 | 只有 5 张表、只读查询，ORM 增加抽象层 |
| Pandas | 可选 | 当前结果规模小，列表 + Plotly 足够；后续做复杂数据处理再引入 |
| LangChain / LlamaIndex | 否 | 抽象层会隐藏提示词与上下文控制，不利于调试与隐私控制 |
| sqlparse | 否 | 只能做词法层面判断，无法可靠提取表名与语句类型 |
| JWT | 否 | 单机单进程，内存会话足够；JWT 增加密钥管理负担 |
| 子进程执行 SQL | 否 | 超时用 SQLite 进度回调即可满足；子进程增加复杂度 |

## 4. 数据访问层

### 4.1 连接管理

**连接串**

```python
sqlite3.connect("file:/abs/path/db/ecommerce.db?mode=ro", uri=True)
```

**连接设置**

| 设置 | 值 | 目的 |
|---|---|---|
| `uri` | True | 启用只读模式 |
| `row_factory` | `sqlite3.Row` | 按列名访问 |
| `timeout` | 2 秒 | 等待锁的上限 |
| `PRAGMA query_only` | ON | 双重保险，即使连接串失效也不能写 |
| `PRAGMA foreign_keys` | ON（仅造数脚本） | 保证造数时关系完整 |

**生命周期**

- 每次请求创建连接，用完即关（SQLite 连接开销极小）
- 不使用全局共享连接，避免 Streamlit 多线程下的线程安全问题
- 连接失败视为系统错误，返回 `E_DB_UNAVAILABLE`

### 4.2 Schema 抽取

**抽取内容**

| 内容 | 查询 |
|---|---|
| 表清单 | `SELECT name FROM sqlite_master WHERE type='table'` |
| 字段 | `PRAGMA table_info(?)` |
| 外键 | `PRAGMA foreign_key_list(?)` |
| 索引 | `PRAGMA index_list(?)` |
| 示例值 | `SELECT DISTINCT col FROM table LIMIT 5`（仅非 PII 字段） |

**SchemaMeta 结构**

```
SchemaMeta
├── tables: list[TableMeta]
│   ├── name
│   ├── columns: list[ColumnMeta]
│   │   ├── name, type, not_null, primary_key
│   │   └── sample_values: list[str]
│   └── foreign_keys: list[ForeignKey]
```

**缓存**

- 启动时加载一次，缓存在应用级对象中
- 以数据库文件 `mtime` 作为失效依据：变化时重新加载
- 示例值查询失败不阻塞启动，降级为无示例

**PII 处理**

- 示例值抽取前先查语义层 PII 标记，PII 字段**不取示例值**
- 字段名与类型可进入模型上下文；数据值不进入

### 4.3 语义层加载与校验

**加载顺序**

1. 读取 `config/semantic/tables.yaml` 与 `metrics.yaml`
2. 与 `SchemaMeta` 做交叉校验
3. 校验失败 → 启动中止，打印具体差异

**校验规则**

| 规则 | 失败处理 |
|---|---|
| YAML 中的表必须在数据库中 | 启动失败 |
| YAML 中的字段必须存在 | 启动失败 |
| 指标引用的 `time_field` 必须存在 | 启动失败 |
| 外键关系与 `PRAGMA foreign_key_list` 一致 | 警告 |
| PII 字段必须在 `privacy.yaml` 有对应规则 | 启动失败 |
| 同义词不得跨指标重复 | 启动失败 |

**合并结果**

```
SemanticMeta
├── tables: dict[str, TableDescription]
├── metrics: dict[str, MetricDefinition]
├── synonyms: dict[str, str]           # 同义词 → 标准名
└── time_rules: list[TimeRule]
```

### 4.4 执行器与超时

**执行流程**

1. 接收 `GuardResult.sql` 与参数绑定 `params`
2. 创建只读连接
3. 设置进度回调：`conn.set_progress_handler(check_deadline, 1000)`
4. 执行：`cursor.execute(sql, params)`
5. 取前 `max_rows + 1` 行，判断是否截断
6. 组装 `ExecutionResult`
7. 关闭游标与连接

**超时实现**

```
deadline = monotonic() + timeout_seconds

def check_deadline():
    return 1 if monotonic() > deadline else 0
```

- 每 1000 条 VM 指令检查一次
- 回调返回非 0 时 SQLite 抛出 `OperationalError: interrupted`
- 统一转换为 `E_SQL_TIMEOUT`

**截断**

- 最多取 `max_rows + 1` 行
- 超过上限时只返回前 `max_rows` 行，并置 `truncated = True`
- 界面提示"结果超过上限，仅展示前 N 行"

**结果模型**

```
ExecutionResult
├── columns: list[ColumnInfo]
│   ├── name, display_name, semantic_type
│   └── is_pii
├── rows: list[list[Any]]
├── row_count: int
├── truncated: bool
├── elapsed_ms: int
└── error: ErrorInfo | None
```

### 4.5 参数绑定

- 所有用户提供的值必须通过参数绑定传入，不拼接到 SQL
- 个体查询使用命名参数 `:subject_id`
- 执行器只接受来自 `GuardResult` 的参数名，拒绝额外参数
- 参数值不写入日志

## 5. SQL 安全层

### 5.1 校验流水线

```
输入 SQL
  │
  ├─ 1. 空值与长度检查
  ├─ 2. sqlglot 解析（read="sqlite"）
  ├─ 3. 语句数量检查（必须为 1）
  ├─ 4. 语句类型检查（仅 SELECT / WITH … SELECT）
  ├─ 5. 危险表达式检查（写操作、PRAGMA、ATTACH）
  ├─ 6. 表名提取 + 白名单校验
  ├─ 7. 列名提取 + 角色 PII 策略
  ├─ 8. 字面量 PII 检查
  ├─ 9. 个体查询参数检查（必须使用 :subject_id）
  ├─ 10. LIMIT 补全
  └─ 输出 GuardResult
```

### 5.2 校验规则实现

| 检查项 | 实现方式 | 失败码 |
|---|---|---|
| 语句数量 | `sqlglot.parse(sql, read="sqlite")`，长度必须为 1 | `E_SQL_MULTI` |
| 语句类型 | 根节点为 `exp.Select`，或 `exp.With` 且主体为 SELECT | `E_SQL_TYPE` |
| 危险表达式 | AST 中不得出现 `Insert/Update/Delete/Create/Drop/Alter/Command` | `E_SQL_FORBIDDEN` |
| 危险关键字 | 词法兜底：PRAGMA、ATTACH、DETACH、VACUUM | `E_SQL_FORBIDDEN` |
| 表白名单 | `expression.find_all(exp.Table)` 提取表名，比对配置 | `E_SQL_TABLE` |
| 列策略 | 提取 SELECT 表达式中的列；analyst 不得选择 PII 列 | `E_SQL_PII_COLUMN` |
| 星号 | `SELECT *` 在 analyst 角色下拒绝（无法静态判断是否含 PII） | `E_SQL_STAR` |
| 字面量 PII | 提取字符串字面量，与客户名/手机号索引做哈希比对 | `E_SQL_PII_LITERAL` |
| 个体参数 | `scope=individual` 时必须包含 `:subject_id` | `E_SQL_SUBJECT_PARAM` |
| LIMIT | 无 LIMIT 时在 AST 上追加 1000 | 自动修正 |

### 5.3 sqlglot 使用要点

- 解析失败抛 `ParseError` → 视为 `E_SQL_PARSE`，触发一次修复
- 表名提取需处理别名：`Table.name` 为物理表名，`alias` 不参与白名单
- 列名提取只检查 SELECT 投影，不检查 WHERE（WHERE 允许用 PII 列做筛选，但值必须参数化）
- 方言固定 `sqlite`，避免模型输出其他方言时误判
- 生成规范化 SQL 时使用 `expression.sql(dialect="sqlite")`

### 5.4 角色 PII 策略

| 角色 | SELECT PII 列 | 说明 |
|---|---|---|
| analyst | 禁止 | 统计查询不需要客户身份 |
| customer | 仅本人相关查询允许 | 展示前仍脱敏 |
| admin | 允许 | 展示前仍脱敏 |

**防御纵深**：即使 SQL 层放行，`guard/privacy` 仍会在结果上执行脱敏；两层都失效的概率极低。

### 5.5 字面量 PII 检查

- 启动时构建客户 PII 索引：姓名、手机号、邮箱的 HMAC 集合
- 从 AST 中提取所有字符串字面量，逐个 HMAC 后比对
- 命中 → 拒绝，要求改用 `:subject_id` 参数
- 索引只存在内存，不落盘、不打印

### 5.6 LIMIT 补全

```
if not expression.args.get("limit"):
    expression = expression.limit(max_rows)
```

- 已有 LIMIT 且小于上限：保留
- 已有 LIMIT 且大于上限：改为上限
- 子查询内的 LIMIT 不影响外层判断

### 5.7 失败处理

| 失败 | 处理 |
|---|---|
| 语法解析失败 | 允许一次修复 |
| 类型/白名单/PII 违规 | 允许一次修复；仍失败则拦截 |
| 修复后仍违规 | 拦截 + 审计 `sql_blocked` |
| 拦截时 | 不执行、不回显 SQL、返回统一文案 |

## 6. LLM 调用层

### 6.1 客户端封装

**接口**

```
LLMClient.complete_json(
    messages: list[Message],
    schema: type[BaseModel],
    temperature: float,
    max_retries: int,
) -> BaseModel
```

**职责**

- 统一鉴权、超时、重试
- 结构化输出校验
- token 用量统计
- 错误归一化

**配置**

| 项 | 说明 |
|---|---|
| base_url | 兼容 OpenAI 协议的地址 |
| api_key | 从环境变量读取，不写配置文件 |
| model | 模型名称 |
| timeout | 60 秒 |
| max_retries | 2 次（仅网络类错误） |
| temperature | SQL 0.0，摘要 0.3，意图 0.0 |

### 6.2 结构化输出

**优先方案**

- 使用 `response_format={"type": "json_object"}`（供应商支持时）
- 提示词中给出 JSON Schema 的文字说明与示例

**兜底方案**

1. 从返回文本中提取第一个 JSON 对象（处理 ```json 代码块）
2. 用 Pydantic 校验
3. 校验失败 → 追加错误信息重试 1 次
4. 仍失败 → `E_LLM_INVALID_JSON`

**校验失败反馈**

```
上一次输出无法解析为约定 JSON：<错误摘要>
请只输出 JSON，不要包含解释文字。
```

### 6.3 重试与超时

| 错误类型 | 重试 | 策略 |
|---|---|---|
| 网络超时 | 是 | 指数退避 + 抖动，最多 2 次 |
| 429 限流 | 是 | 读取 `Retry-After`，最多 2 次 |
| 5xx | 是 | 退避重试 |
| 4xx（鉴权/参数） | 否 | 直接失败 |
| JSON 校验失败 | 是 | 带错误反馈重试 1 次 |

**超时分层**

- 连接超时 10 秒
- 读取超时 60 秒
- 单轮总预算 120 秒（含重试）

### 6.4 提示词渲染

- 模板文件放在 `config/prompts/`，使用 Jinja2
- 渲染时注入：schema 文本、指标文本、few-shot、历史、问题
- 渲染前做 PII 检查：渲染后的字符串不得命中 PII 索引
- 渲染结果不写入普通日志；只记录模板名、长度、token 估算

### 6.5 Token 预算

| 部分 | 预算（token） |
|---|---|
| system 规则 | 400 |
| schema 上下文 | 2500 |
| 指标与同义词 | 800 |
| few-shot | 1500 |
| 历史 | 800 |
| 问题 | 200 |
| 输出预留 | 800 |
| **合计** | **约 7000** |

**裁剪顺序**（超预算时）

1. 历史轮次从最旧开始丢弃
2. few-shot 从 5 条减到 3 条
3. 示例值移除
4. schema 只保留与问题相关的表
5. 仍超 → 返回生成失败，不强行截断到语义残缺

## 7. 核心编排

### 7.1 状态机实现

**状态枚举**

```
IDLE
AUTHENTICATING
UNDERSTANDING
CLARIFYING
AUTHORIZING
GENERATING
GUARDING
EXECUTING
REPAIRING
PRESENTING
DONE
DENIED
NO_DATA
FAILED
```

**单轮处理伪代码**

```
def handle(session, question):
    trace = Trace(turn_id=uuid4())
    sanitized, subject = local_pii_scan(question)

    intent = intent_recognize(sanitized, session.history)
    if intent.type != "query":
        return reply_chitchat_or_unsupported(intent)

    decision = authorize(session.principal, intent, subject)
    if not decision.allowed:
        audit.deny(session.principal, intent, subject)
        return denied(decision.uniform_message)

    if intent.missing_slots:
        session.pending = Clarification(intent, sanitized)
        return clarify(intent.missing_slots)

    context = build_prompt_context(intent, session.history)
    plan = nl2sql(context)
    guard_result = sql_guard.check(plan, session.principal, intent, subject)
    if not guard_result.ok:
        audit.sql_blocked(...)
        return blocked()

    result = executor.run(guard_result, params=guard_result.params)
    attempts = 0
    while result.error and attempts < 2:
        plan = repair(question, plan, result.error)
        guard_result = sql_guard.check(plan, ...)
        result = executor.run(guard_result, ...)
        attempts += 1

    if result.error:
        return failed(result)

    if result.row_count == 0:
        maybe_repair_empty(...)

    provenance.write(turn_id, sanitized, guard_result.sql, result, attempts)
    masked = privacy.mask(result, session.principal)
    chart = chart.select(masked)
    summary = summary.generate(sanitized, masked)
    return answer(guard_result.sql, masked, chart, summary, provenance)
```

### 7.2 步骤契约

| 步骤 | 输入 | 输出 | 失败 |
|---|---|---|---|
| `local_pii_scan` | 原始问题 | 脱敏问题 + `Subject` | 无法判定 → 按个体处理 |
| `intent_recognize` | 脱敏问题 + 历史 | `IntentResult` | 降级为 query |
| `authorize` | Principal + Intent + Subject | `AuthDecision` | 默认拒绝 |
| `build_prompt_context` | Intent + 历史 + 元数据 | `PromptContext` | 超预算 → 生成失败 |
| `nl2sql` | PromptContext | `SQLPlan` | 生成失败 |
| `sql_guard.check` | SQLPlan + Principal + Intent | `GuardResult` | 拦截 |
| `executor.run` | GuardResult + params | `ExecutionResult` | 错误/超时 |
| `repair` | 问题 + 失败 SQL + 错误 | 新 SQLPlan | 放弃 |
| `privacy.mask` | ExecutionResult + Principal | 脱敏结果 | 隐藏字段 |
| `chart.select` | 脱敏结果 | ChartSpec | 降级表格 |
| `summary.generate` | 问题 + 脱敏结果 + 口径 | 文本 | 省略摘要 |

### 7.3 错误传播

- 内部使用带错误码的异常或 `Result` 类型，不跨模块抛裸异常
- 错误码在 `infra/errors.py` 统一定义
- `orchestrator` 把错误码映射为用户文案（见功能设计文档 3.3）
- 未预期异常统一捕获为 `E_INTERNAL`，记录堆栈到系统日志，界面只显示通用文案

### 7.4 会话存储

**存储位置**

- `st.session_state` 保存 UI 态（当前页面、输入框、busy）
- `SessionStore`（进程内字典）保存业务态，键为 `session_id`

**业务态结构**

```
Session
├── session_id
├── principal
├── created_at
├── last_active_at
├── history: list[Turn]
├── pending_clarification: Clarification | None
└── reset_marker: int
```

**生命周期**

- 创建：登录成功
- 过期：空闲 30 分钟或总时长 8 小时
- 清理：惰性清理 + 定时扫描（每分钟）
- 同一会话串行处理：`Session.lock` 保证单请求

**历史窗口**

- 保存最近 10 轮
- 送入模型最近 5 轮
- 被拒绝的轮次不进入可继承上下文

## 8. 关键算法

### 8.1 个体查询识别与主体解析

**两阶段**

1. **本地规则扫描**（不调用模型）
   - 正则匹配手机号、邮箱
   - 客户名索引精确匹配
   - 关键词："我的"、"某客户"、"这个客户"、"他的"、"她的"
   - 客户编号格式匹配
2. **模型判定**（使用脱敏后的问题）
   - 输出 `scope` 与 `subject.type`
   - 与本地结果合并：本地命中个体 → 强制个体（宁可误拒）

**客户名索引**

```
NameIndex
├── by_name: dict[str, list[customer_id]]
├── by_phone: dict[str, customer_id]
├── by_email: dict[str, customer_id]
└── pii_hash_set: set[hmac_sha256(...)]
```

- 启动时从数据库加载，仅驻留内存
- 只做精确匹配，不做模糊匹配（避免误伤分析类问题）
- 同名多人 → 标记 `ambiguous`，按"不存在或无权"处理

**主体解析结果**

```
Subject
├── type: name | phone | email | customer_id | self
├── customer_id: str | None
├── hash: str
└── ambiguous: bool
```

**customer 角色的"我的"**：直接映射为 `principal.customer_id`，无需姓名匹配。

### 8.2 问题脱敏与占位符替换

**流程**

1. 定位问题中的 PII 片段（姓名、手机号、邮箱、编号）
2. 替换为占位符：`[客户]`、`[手机号]`、`[邮箱]`、`[客户编号]`
3. 脱敏后的问题用于：意图识别、NL2SQL、摘要、日志、溯源
4. 原始片段只在 `Subject` 中保留 `customer_id` 与哈希

**示例**

```
原始：客户张三买了什么
脱敏：客户[客户]买了什么
模型：scope=individual, subject=[客户]
NL2SQL：SELECT ... FROM orders WHERE customer_id = :subject_id
```

**价值**

- 原始 PII 不进入任何模型上下文
- SQL 中不存在姓名/手机号字面量
- 日志与溯源天然不含 PII

### 8.3 时间范围解析

**规则优先**

| 表达 | 区间 |
|---|---|
| 今天 | 当日 00:00:00 ～ 23:59:59 |
| 昨天 | 前一日 |
| 本周 | 周一 00:00 ～ 当前 |
| 本月 | 当月 1 日 ～ 当前 |
| 上月 | 上一个自然月整月 |
| 近 N 天 | 今天往前 N-1 天 00:00 ～ 现在 |
| 今年 | 1 月 1 日 ～ 当前 |
| 去年 | 去年整年 |
| 双 11 | 11 月 11 日 00:00 ～ 23:59 |
| 自定义区间 | 解析起止日期 |

**实现**

- 模型只负责抽取时间**表达**（如"上一个自然月"），不负责计算区间
- 计算由本地 `TimeResolver` 完成，使用 `datetime` + `calendar`
- 时区固定 `Asia/Shanghai`
- 无法解析 → `missing_slots=["time_range"]`

**输出**

```
TimeRange
├── start: datetime
├── end: datetime
├── label: str
└── field: order_date | pay_date | refund_date
```

### 8.4 上下文组装

**表筛选**

1. 从指标定义找到所需表
2. 从维度/筛选字段找到所属表
3. 从外键关系补齐连接路径上的中间表
4. 无法确定时回退到全部 5 张表

**文本组装顺序**

```
1. 角色与规则
2. 表结构（人话描述 + 字段 + 关系）
3. 指标口径与同义词
4. few-shot
5. 历史（最近 5 轮，已脱敏）
6. 当前问题（已脱敏）
```

**few-shot 选择**

| 意图特征 | 选择示例 |
|---|---|
| 含时间过滤 | 单表时间聚合 |
| 含"排名/Top" | 分组排序 |
| 含品类/商品 | 多表 join |
| 含"占比" | 分组占比 |
| 含"率/人均" | 比率计算 |

- 默认 5 条，超预算先减到 3 条
- few-shot 中的客户值一律使用占位符

### 8.5 自修复循环

**触发**：执行错误或超时。

**循环**

```
for attempt in range(1, max_repair + 1):
    plan = repair_prompt(question, last_plan, error, schema)
    guard = sql_guard.check(plan, principal, intent, subject)
    if not guard.ok:
        return blocked(guard.reason)
    result = executor.run(guard)
    if not result.error:
        return result, attempt
return result, max_repair
```

**意图漂移检测**

- 比较修复前后的 `time_range`、`metric_used`、`scope`
- 任一发生变化 → 拒绝该次修复，按修复失败处理
- 目的：防止模型通过修改时间范围或指标来"修好"查询

**修复提示词要素**

- 原问题（脱敏）
- 上一次 SQL
- 数据库错误原文（去掉连接信息）
- schema 片段
- 明确要求：只修语法/字段/类型，不改变业务意图

### 8.6 空结果判定

**判定流程**

1. `row_count > 0` → 正常
2. `row_count == 0`：
   - 聚合查询且返回 0 → 如实展示 0
   - 明细查询无行 → 检查 SQL 是否包含用户未明确要求的过滤条件
   - 若存在额外过滤 → 允许一次修复，提示"检查过滤条件是否过严"
   - 否则 → 返回无数据
3. 修复后仍为 0 → 无数据

**额外过滤判定**

- 从 `IntentResult.entities.filters` 与 SQL WHERE 条件做比对
- 只允许移除/放宽**未被用户显式要求**的条件
- 用户显式的时间范围与筛选一律不得改动

### 8.7 图表选型

**输入**

- `ExecutionResult` 列语义：`time` / `dimension` / `measure`
- 行数、类别数、是否含负值

**决策树**

```
if rows == 1 and 1 measure                         -> metric
elif has time column and 1+ measure               -> line
elif has dimension and measure:
    if measure is share and categories <= 6 and all >= 0 -> pie
    elif categories <= 12                          -> bar
    else                                           -> bar(horizontal, top 20)
elif detail columns >= 3 and no measure            -> table
else                                               -> table
```

**输出**

```
ChartSpec
├── type
├── x, y, series
├── title
├── reason
└── plotly_config: dict
```

**降级**

- Plotly 配置校验失败 → `table`
- 类别过多 → 取 Top 20 并在标题注明
- 含负值 → 禁用饼图

### 8.8 脱敏算法

**注册表**

- 来源：语义层 `pii: true` + `config/privacy.yaml` 的规则
- 未登记但字段名疑似 PII（`name`、`phone`、`email`、`address`、`id_card`）→ 默认脱敏

**各类型实现**

| 类型 | 算法 |
|---|---|
| 姓名 | 取首字符 + `*`；单字姓名 → `*` |
| 手机号 | 保留前 3 后 4，中间 `****` |
| 邮箱 | `local[0] + "***@" + domain` |
| 地址 | 按省/市切分，保留到市；无法解析则保留前 2 字符 |
| 生日 | 计算年龄，映射到年龄段（<18、18-24、25-34…） |
| 客户编号 | `hmac_sha256(salt, id)[:12]` |

**应用顺序**

```
SQL 聚合 → ExecutionResult → 脱敏 → 图表/摘要/LLM/日志/UI
```

**注意**

- 脱敏在聚合之后，不影响数值正确性
- 图表使用的数据与表格一致（都是脱敏后）
- 摘要提示词只看到脱敏结果

### 8.9 K 匿名（可选）

**适用**：结果包含维度 + 计数，且计数 < K。

**策略**

- 将小分组合并为"其他"
- 或直接隐藏该行，并注明"部分分组因样本过少已隐藏"
- 仅作用于展示，不改动底层数据

**配置**

```
k_anonymity:
  enabled: false
  k: 5
```

## 10. 日志、溯源与审计

### 10.1 通用日志

**格式**：JSON Lines，每行一个事件。

**字段**

```json
{
  "ts": "2026-10-22T10:00:00+08:00",
  "level": "INFO",
  "event": "sql_executed",
  "turn_id": "t_...",
  "session_id": "s_...",
  "principal_id": "u_1001",
  "duration_ms": 42,
  "data": {"row_count": 8, "repair_attempts": 0}
}
```

**级别**

| 级别 | 用途 |
|---|---|
| DEBUG | 开发调试，默认关闭 |
| INFO | 关键步骤与耗时 |
| WARNING | 降级、配置不一致、修复触发 |
| ERROR | 执行失败、模型不可用 |

**脱敏要求**

- 不记录问题原文（只记录脱敏版本）
- 不记录 SQL 参数值
- 不记录模型提示词全文
- 不记录密码、密钥、连接串

### 10.2 溯源

**文件**：`logs/provenance-YYYY-MM-DD.jsonl`

**写入时机**：成功执行后、返回答案前。

**记录内容**

- `turn_id`
- 脱敏后的问题
- 完整 SQL
- 表与字段
- 行数、是否截断、耗时
- 修复次数
- 脱敏字段列表
- 摘要
- 语义层版本

**可复现性**

- SQL 使用命名参数；溯源中同时记录参数**名称**
- 个体查询的参数值不记录（属于 PII），因此个体查询无法仅凭溯源完全复现
- 聚合查询的参数值可记录（如省份、日期），保证可复现
- 这一取舍在文档中明确标注

### 10.3 审计

**文件**：`logs/audit-YYYY-MM-DD.jsonl`

**写入时机**：登录、登出、权限判定、SQL 拦截、会话过期。

**记录内容**

- `audit_id`、`timestamp`
- `principal_id`、`role`
- `action`：login_success / login_failed / query_allowed / query_denied / sql_blocked / logout / session_expired
- `question_masked`
- `target_subject_hash`
- `decision`、`reason`
- `sql`（仅放行时）、`row_count`

**写入实现**

- `os.open(path, O_APPEND | O_CREAT | O_WRONLY, 0o600)`
- 单行写入，`flush` + `fsync`
- 文件按天切分
- 写入失败：记录系统日志，不阻塞主流程

**防篡改（可选）**

- 每条记录包含 `prev_hash`，形成哈希链
- 提供离线校验脚本 `scripts/verify_audit.py`
- 默认关闭，作为 P2 增强

### 10.4 日志检索

- 以 `turn_id` 串联一轮对话的所有事件
- 以 `session_id` 查看会话轨迹
- 以 `principal_id` 查看某个账号的行为
- 不提供界面查询，使用命令行工具（`jq`、`grep`）

## 11. 安全实现

### 11.1 认证

**密码校验**

- `argon2-cffi` 的 `PasswordHasher.verify(hash, password)`
- 校验失败不区分原因
- 校验耗时保持稳定（argon2 本身较慢，天然抵御时序攻击）

**会话令牌**

- 登录成功生成 `secrets.token_urlsafe(32)`
- 令牌只存在 `st.session_state` 与服务端 `SessionStore`
- 不写 Cookie、不写 URL

**失败锁定**

- 进程内字典：`username -> (fail_count, locked_until)`
- 连续 5 次失败 → 锁定 5 分钟
- 登录成功清零
- 重启后清空（可接受，本地演示）

### 11.2 授权

**判定顺序**

1. 角色是否存在
2. 角色是否允许该 scope
3. customer 角色的 subject 是否等于本人
4. 目标是否解析成功且唯一
5. 全部通过才放行

**失败一律拒绝**，不区分原因，对外统一文案。

**审计**：每次判定都写审计，allowed 与 denied 均记录。

### 11.3 防枚举

| 措施 | 实现 |
|---|---|
| 统一文案 | 拒绝与不存在共用常量 |
| 不查库 | 拒绝路径在 `authorize` 返回，不进入 executor |
| 响应结构 | 同一 `ChatAnswer` 结构，`sql`、`table`、`chart` 均为空 |
| 响应耗时 | 拒绝路径不调用模型、不查库；与"不存在"路径一致 |
| 同名多人 | 不提示"有多个同名"，直接拒绝 |
| 错误日志 | 不区分对外文案，内部分原因码只进审计 |

### 11.4 提示词注入

**攻击面**

- 用户问题中要求"忽略之前的指令"
- 要求输出系统提示词
- 要求执行写操作

**防御**

1. 本地 SQL 校验为最终权威，模型输出不可信
2. 提示词明确"只输出 JSON"，但不仅依赖提示词
3. 输入长度限制 200 字
4. 检测并剥离常见注入模式（可选）
5. 系统提示词不包含密钥与内部路径
6. 模型返回中的危险内容不直接展示

### 11.5 密钥管理

- `LLM_API_KEY` 只从环境变量读取
- 不写入代码、配置、日志
- `.env` 加入 `.gitignore`
- 日志中对密钥做正则脱敏（兜底）

| `logs/*.jsonl` | 0600 |
| `db/ecommerce.db` | 0644（只读查询，无敏感明文以外内容） |

## 18. 技术风险

| 风险 | 影响 | 对策 |
|---|---|---|
| Streamlit 重跑导致重复请求 | 重复扣费、重复查询 | `busy` 标志 + 只在提交分支执行 |
| sqlglot 对特殊 SQL 解析失败 | 误拦截 | 解析失败允许一次修复；保持 SQL 简洁 |
| SQLite 进度回调超时精度 | 长查询无法立即中断 | 每 1000 指令检查；必要时降低步长 |
| 模型 JSON 输出不稳定 | 流程中断 | JSON 模式 + 重试 + Pydantic 校验 |
| 姓名精确匹配误伤 | 分析类问题被误判为个体 | 仅精确匹配；误拒可接受（fail closed） |
| 提示词注入 | 越权/写操作 | 本地 SQL 校验为最终防线 |
| 日志泄露 PII | 隐私事故 | 脱敏前置 + 日志扫描测试 |
| 模型供应商兼容性 | JSON 模式/参数不支持 | 能力探测 + 兜底解析 |
| 依赖版本漂移 | 构建失败 | `uv.lock` 锁定 |
| 金额使用 REAL 的精度误差 | 展示尾差 | 计算后统一四舍五入到 2 位；生产可改整数分 |

## 附录 B · 数据定义（DDL）

> 以下为数据库结构定义，供建表脚本使用，不包含应用逻辑。

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE customers (
    customer_id   TEXT PRIMARY KEY,
    customer_name TEXT NOT NULL,
    gender        TEXT,
    birth_date    DATE,
    province      TEXT,
    city          TEXT,
    register_date DATE NOT NULL,
    member_level  TEXT CHECK (member_level IN ('普通','银卡','金卡','钻石'))
);

CREATE TABLE products (
    product_id   TEXT PRIMARY KEY,
    product_name TEXT NOT NULL,
    category     TEXT NOT NULL,
    sub_category TEXT,
    brand        TEXT,
    list_price   REAL CHECK (list_price >= 0),
    cost_price   REAL CHECK (cost_price >= 0)
);

CREATE TABLE orders (
    order_id         TEXT PRIMARY KEY,
    customer_id      TEXT NOT NULL REFERENCES customers(customer_id),
    order_date       DATETIME NOT NULL,
    pay_date         DATETIME,
    status           TEXT NOT NULL CHECK (status IN ('待支付','已支付','已发货','已完成','已取消','已退款')),
    channel          TEXT CHECK (channel IN ('App','小程序','PC','线下')),
    shipping_province TEXT,
    pay_amount       REAL CHECK (pay_amount >= 0),
    discount_amount  REAL CHECK (discount_amount >= 0)
);

CREATE TABLE order_items (
    item_id     TEXT PRIMARY KEY,
    order_id    TEXT NOT NULL REFERENCES orders(order_id),
    product_id  TEXT NOT NULL REFERENCES products(product_id),
    quantity    INTEGER CHECK (quantity > 0),
    unit_price  REAL CHECK (unit_price >= 0),
    item_amount REAL CHECK (item_amount >= 0)
);

CREATE TABLE refunds (
    refund_id     TEXT PRIMARY KEY,
    order_id      TEXT NOT NULL REFERENCES orders(order_id),
    refund_date   DATETIME NOT NULL,
    refund_amount REAL CHECK (refund_amount >= 0),
    reason        TEXT
);

CREATE INDEX idx_orders_order_date ON orders(order_date);
CREATE INDEX idx_orders_customer   ON orders(customer_id);
CREATE INDEX idx_orders_status     ON orders(status);
CREATE INDEX idx_items_order       ON order_items(order_id);
CREATE INDEX idx_items_product     ON order_items(product_id);
CREATE INDEX idx_refunds_order     ON refunds(order_id);
CREATE INDEX idx_refunds_date      ON refunds(refund_date);
```

**说明**

- 日期时间统一存为 `YYYY-MM-DD HH:MM:SS` 文本，便于 SQLite 比较与排序
- 金额使用 `REAL`，计算后统一四舍五入到 2 位小数
- 生产场景可改为整数分，避免浮点误差
- 时区统一按 `Asia/Shanghai`

```

[输出格式]

  "scope": "aggregate|individual",
