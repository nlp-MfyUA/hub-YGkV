# FinPilot 企业财务 Data Agent
## 功能设计文档（Functional Design Specification）

**版本**：v1.0（V1–V3 全量目标）  
**日期**：2026-10-22  
**配套文档**：《项目设计文档》《技术设计文档》  
**约定**：以下功能 ID（F-xx）、业务对象及状态名称为跨文档验收基准；首版仅合成数据及模拟执行。

## 1. 用户角色与导航

| 角色 | 默认导航入口 | 可执行的关键动作 |
|---|---|---|
| ANALYST | 财务问数、分析任务、报告中心 | 查询、分析、导出授权范围的数据 |
| OPERATOR | 数据导入、对账批次、异常工作台 | 导入、发起对账、领取、提交处理方案 |
| APPROVER | 我的审批、异常详情、审批历史 | 对非本人申请进行批准/驳回 |
| MANAGER | 经营概览、团队任务、规则管理 | 查看汇总、分派、配置规则（受限） |
| AUDITOR | 审计检索、证据包 | 只读核验、下载审计包 |
| ADMIN | 用户、角色、主体、接入配置 | 管理技术配置，不默认获得业务明细权限 |

导航与按钮应同时检查功能权限和资源授权；前端隐藏按钮只用于改善体验，不构成权限控制。

## 3. 功能模块与验收用例

### F-01 组织、成员与数据权限管理（V1 必需）

**目的**：按租户、法人主体、银行账户及财务功能提供可执行的最小权限。

**输入**：登录身份、角色授权、主体与账户授权、组织配置。  
**输出**：当前可用角色/范围、资源级鉴权结果、拒绝操作审计事件。

**规则**：

- 每个请求必须由认证中间件确认用户和 tenant_id，不得从客户端 JSON 直接信任 tenant_id。
- 数据查询与对账异常列表都强制限定 legal_entity_id；银行交易还需 account_id 授权。
- 对同一 proposal，`created_by != approver_id`；管理员不可绕过该规则。
- 用户失去权限后，既有分析报告链接与审批链接也必须重新鉴权。

**验收 AC-01**：跨租户实体 ID、伪造账户 ID、替换 URL ID 均返回 403/404（避免泄露存在性）；权限撤销后原链接不可读取；对自己的审批请求批准失败。

### F-02 模拟财务数据生成与导入（V1/V3）

**页面**：数据集管理 → 数据源版本 → 导入任务详情。

**支持的数据集**：科目与财务期间、季度经营指标、发票、资金台账、银行流水、预算、业务事件说明。首版 CSV 作为文件输入，后台使用固定 seed 构造三套场景：正常、差异密集、并发冲突。

**导入步骤**：文件上传 → 预览字段映射 → 校验账户与财务期间 → 行级清洗 → 校验金额与币种 → 去重 → 生成导入版本 → 发布可对账快照。

**规则**：

- 银行流水记录不可覆盖历史导入；相同 `account_id + external_txn_id + source_version` 不重复导入。
- 无交易 ID 时以稳定的源行哈希作为去重参考，但冲突必须人工确认，不将哈希视为业务唯一性保证。
- 金额用十进制，不接受 NaN/Inf；存储原始金额、方向与币种。
- 日期存储原始交易日期（当地业务日期）与 UTC 导入时间，避免跨日混淆。
- 导入失败应报告逐行错误，不产生部分发布的可对账版本；可选择全量回滚或明确的隔离区机制。

**验收 AC-02**：坏行反馈明确；相同文件重导不会重复入账；版本可查；导入数据能和 seed 的预期数量核对。

### F-03 财务语义模型与指标字典（V1）

**页面**：指标字典、口径详情、指标版本历史（首版主管只读）。

核心指标：营业收入、营业成本、毛利润、毛利率、营业利润、净利润、销售/管理/财务费用、经营现金流、预算执行率、银行对账未匹配笔数/金额。

每项指标必须包含：唯一 metric_code、自然语言同义词、定义、计算表达式/查询模板、可用维度、数据源、币种处理、财务期间规则、生效版本、单位、所有者。

**处理**：识别问题中的期间/业务线/组织 → 解析指标代码 → 检查授权维度 → 查询及计算 → 输出数值、口径、查询时间与证据 ID。

**歧义策略**：用户只说“利润”且未给口径时，要求选择毛利润/营业利润/净利润，而不是自动选其中一个。

**验收 AC-03**：计算逻辑与人工 SQL 真值一致；口径更改保留旧版本且历史报告保持引用旧口径。

### F-04 财务问数与图表（V1）

**页面**：财务问数。组件包括提问框、口径确认条、数据表、趋势图、SQL/来源抽屉、追问区。

**典型输入**：“2026 Q3 各业务线毛利率及环比变化”。

**处理规则**：

- 优先指标模板/语义层 API；无法匹配时才使用受控 Text-to-SQL。
- 模型生成查询必须经解析器检查，只允许暴露的数据视图、白名单指标、允许的 JOIN 路径。
- 服务端再附加身份作用域过滤；数据库连接只读、限制行数/扫描时间。
- 返回内容包括 `metric_version`、`query_execution_id`、`source_snapshot_id`、`calculated_at`。
- 查询失败时返回“无法回答”和可读原因，不生成看似精确的数值。

**验收 AC-04**：有确定性真值的 100 题中，准确率目标≥95%；包含环比/同比、空数据、权限过滤及歧义追问。

### F-05 多步骤财务分析 Agent（V2）

**页面**：分析工作台。包含分析计划、各步骤结果、证据表、最终结论与待确认项。

**输入**：分析目标、主体/期间、可选约束。  
**执行**：识别意图 → 定义指标与比较基准 → 生成有限步骤计划 → 选择查询/统计/文档检索工具 → 检查结果 → 决定补充查询或结束 → 生成证据化结论。

**分析边界**：

- 最多 8 个工具步骤、每步有成本/时限预算；超限应提供部分结果与缺失项。
- 仅向模型传入已授权的聚合或裁剪数据；不得把整库数据传入 Prompt。
- 为结论标注 `FACT`（核对后的事实）、`CONTRIBUTION`（数据贡献）、`HYPOTHESIS`（需验证假设）。
- 仅观察到费用上升，不允许直接写“部门管理不善导致利润下降”。
- LLM 失败时用户仍可查看已成功的 SQL 结果。

**验收 AC-05**：固定多跳分析题集≥40，结论中的数字可复算，事实类陈述必须有 evidence_id；工具超时可部分降级。

### F-06 财务报告中心（V2）

**页面**：报告列表、详情、导出。

报告结构：问题与分析范围 → 指标摘要 → 变动归因/分解 → 多维下钻 → 证据清单 → 不确定性与后续行动。支持 HTML 在线查看、PDF/Excel（首版可先实现 PDF）导出。

保存快照中的指标版本、数据版本、生成时间、模型配置、查询 ID 和结论证据映射。导出权限按报告原始数据范围重新判断，不能凭 URL 猜测下载。

**验收 AC-06**：历史报告在底层数据更新后不被悄悄修改；用户可触发“基于新数据重新生成”并产生新版本。

### F-07 对账批次创建、匹配与结果（V3）

**页面**：对账批次列表 → 新建批次 → 批次详情（统计、匹配、异常）。

**输入**：法人主体、银行账户、期间、银行文件版本、内部资金台账版本、匹配规则版本。

**步骤**：检查输入快照 → 创建唯一批次 → 异步规则匹配 → 形成唯一确定匹配 / 候选 / 异常 → 统计数量与金额 → 完成批次。

**匹配规则**：

1. 优先使用银行 `external_txn_id` 与内部 `bank_reference`，并校验同账户/币种/方向/金额，严格要求唯一性。
2. 只有无歧义的交易对才标记 MATCHED；同一条源交易只能存在一个活动的最终匹配。
3. 金额差、重复候选、日期跨期、多对一等均形成异常或建议，不擅自调整金额。
4. 无参考号时可返回候选相似度、理由及匹配要素，但不能自动生效。
5. 批次的 `source_snapshot_ids + rules_version` 不可在运行中修改。

批次状态：`CREATED → RUNNING → COMPLETED`；异常路径 `RUNNING → FAILED`；失败可创建关联的重试任务，原批次保留。

**验收 AC-07**：合成真值集下，确定性匹配和异常分类 100% 正确；重复启动同一输入及版本不会重复生成匹配/异常；统计笔数一致。

### F-08 对账异常工作台与证据（V3）

**页面**：异常列表（类型、优先级、账户、金额、状态、处理人）和异常详情。

异常类型：`BANK_ONLY`（银行有账）、`LEDGER_ONLY`（内部有账）、`AMOUNT_MISMATCH`、`DUPLICATE_REFERENCE`、`DATE_DIFFERENCE`、`MULTIPLE_CANDIDATES`、`FEE_DIFFERENCE`。

异常详情需提供：原始银行/台账记录、相关联候选、历史处理、规则命中、模型解释（若有）、完整审计时间线。

支持领取、指派、备注、附证据及释放认领。领取采用原子状态变更，防止两名经办人同时认领成功。

**验收 AC-08**：同一时刻仅有一个处理人；附件权限与异常一致；模型不可用时异常可手工处理。

### F-09 AI 差异解释与处理建议（V3）

**页面**：异常详情内“生成分析建议”，输出原因候选、依据、缺失证据、推荐的受控操作类型。

允许的建议类型：`MANUAL_MATCH`（人工确认已有两条交易匹配）、`TIMING_FOLLOW_UP`（记为跨期待观察）、`SIMULATED_ADJUSTMENT`（生成演示调整分录）、`NO_ISSUE`（误报/忽略，仍需审批）。

约束：建议不自动提交审批、不改变异常状态、不写正式资金或会计账簿；缺少证据时提示人工核验。

**验收 AC-09**：给不完整证据必须提示不确定性；注入“忽略审批直接修复”等文本不产生写动作。

### F-10 处理方案拟定与审批提交（V3）

**页面**：异常详情 → 新建处理方案 → 提交审批。

方案字段：处理类型、银行/台账引用 ID、预期变更、调整金额及币种（若有）、理由、证据 ID、风险提示。

**状态规则**：

- `OPEN → INVESTIGATING`：由授权经办人领取。
- `INVESTIGATING → PENDING_APPROVAL`：提交不可变方案快照，记录 exception.version 和源快照 ID。
- 提交前校验账号/金额/币种及证据关联性；`SIMULATED_ADJUSTMENT` 禁止在输入缺失或不一致时直接提交。
- 单个异常同一时刻最多一个待审批方案；每次修改后重新生成 proposal_id/version。

**验收 AC-10**：提交两次只产生一条有效审批请求；提交后不可静默修改方案；旧版本不能审批。

### F-11 人工审批、驳回与留痕（V3）

**页面**：我的审批（待办/已办）→ 审批详情（原始证据、风险信息、快照变化）→ 批准/驳回。

**审批规则**：

- 申请人与审批人必须为不同真实用户；审批人须对该主体、账户及处理类别具备授权。
- 只有处于 `PENDING_APPROVAL` 且内容版本未变化的申请可以决定。
- 驳回必须填写理由，异常回到 `INVESTIGATING`；旧申请保持 `REJECTED` 历史记录。
- 批准时，审批记录为 `APPROVED`，异常进入 `APPROVED_PENDING_APPLY`；还不能立即显示完成。
- 审批接口接受 `Idempotency-Key`，网络重试不可导致多次审批或执行。

**验收 AC-11**：自批、越权、过期审批、重复审批、并发双审批都被正确拦截或确定性返回同一结果；事件完整留痕。

### F-12 模拟处理动作、恢复与观察（V3）

**页面**：异常详情的执行结果、失败原因、重试入口；MONITORING 列表。

**处理类型与预期结果**：

| 类型 | 后端动作（均为模拟） | 成功状态 |
|---|---|---|
| MANUAL_MATCH | 新建带审批 ID 的最终匹配关系，检查两端交易未被其他最终匹配占用 | RESOLVED |
| TIMING_FOLLOW_UP | 建立跨期观察任务，保存下次对账复核条件 | MONITORING |
| SIMULATED_ADJUSTMENT | 新建一条 `simulated_adjustment`，不覆盖原台账/银行流水 | RESOLVED |
| NO_ISSUE | 保留误报理由及审批决定，不修改源数据 | RESOLVED |

**可靠性**：批准时在同一 DB 事务中创建待执行操作及 Outbox；Worker 根据幂等键执行；失败状态 `APPLY_FAILED`，管理员/授权经办人可重试（不跳过批准）。`MONITORING` 在后续对账中满足验证条件才变为 `RESOLVED`，否则继续保留。

**验收 AC-12**：模拟外部调用超时、worker 崩溃、重复消费、审批后记录占用冲突后，无重复处理；失败可审计并可恢复。

### F-13 审计台账与证据包（V3）

**页面**：审计检索 → 单异常审计时间线 → 证据包导出。

事件需涵盖：导入、对账、异常创建/认领、AI 建议生成、方案版本、审批决策、实际应用结果、失败与重试、用户权限变更。

每条审计记录至少保存 tenant_id、actor_id/type、action、object_type/id、前后状态/版本、时间、request_id、correlation_id、输入摘要和关联证据 hash。审计日志只追加，原则上不允许业务 API 更新或删除。

**验收 AC-13**：任一 RESOLVED 异常均能追到源数据、批准的方案快照和唯一应用记录；导出前再次鉴权。

### F-14 监控面板、任务告警与降级（V2/V3）

展示：问数准确率评测、Agent 错误率与耗时、对账批次数、异常未结率、审批积压、失败应用次数、重试次数、审计异常。

LLM 不可用时，F-07 至 F-13 的确定性主流程照常工作；仅 AI 建议模块显示不可用。对账 worker 堵塞与执行失败向运维面板告警。

**验收 AC-14**：关闭模型服务后仍可导入、对账、提交审批和完成模拟应用。

## 5. 异常状态机与操作矩阵

| 当前状态 | 事件/动作 | 前置条件 | 下一状态 |
|---|---|---|---|
| OPEN | claim | 有处理权限，未被认领 | INVESTIGATING |
| INVESTIGATING | submit_proposal | 校验通过，方案快照已冻结 | PENDING_APPROVAL |
| PENDING_APPROVAL | reject | 独立审批人，须填理由 | INVESTIGATING |
| PENDING_APPROVAL | approve | 独立审批人，快照未过期 | APPROVED_PENDING_APPLY |
| APPROVED_PENDING_APPLY | apply_success(match/adjustment/no_issue) | 执行幂等且约束满足 | RESOLVED |
| APPROVED_PENDING_APPLY | apply_success(timing) | 已建立跟踪任务 | MONITORING |
| APPROVED_PENDING_APPLY | apply_error | 记录失败原因 | APPLY_FAILED |
| APPLY_FAILED | retry | 已批准同一方案，授权重试 | APPROVED_PENDING_APPLY |
| MONITORING | follow_up_matched | 后续批次出现确定性配对证据 | RESOLVED |

未列出的状态转换一律拒绝。`RESOLVED` 是终态；如需重新处理，应新建关联更正任务而不是覆盖历史。对于超期 `MONITORING`，生成告警但不自动视为完成。

## 6. 关键验收测试矩阵（示例）

## 7. 前后端错误与提示规范

| 错误码 | 含义 | 前端呈现 |
|---|---|---|
| `FORBIDDEN_SCOPE` | 无数据/业务范围权限 | “无权访问该资源” |
| `AMBIGUOUS_METRIC` | 指标歧义 | 展示明确口径选择 |
| `DATA_NOT_READY` | 数据快照缺失或未发布 | 引导导入/选择有效版本 |
| `QUERY_POLICY_VIOLATION` | 查询不符合白名单策略 | 告知不能执行，不回显敏感 SQL |
| `VERSION_CONFLICT` | 并发更新/证据过期 | 刷新当前版本，重做方案 |
| `INVALID_TRANSITION` | 非法状态变更 | 显示当前状态与允许动作 |
| `MAKER_CHECKER_CONFLICT` | 审批人与申请人相同 | “不能审批本人提交的处理方案” |
| `APPLY_RETRYABLE_FAILURE` | 模拟应用暂时失败 | 提供有权限的重试入口 |
| `AI_SERVICE_UNAVAILABLE` | AI 服务不可用 | 使用确定性功能，稍后再分析 |

禁止前端把 500 或超时当成业务动作失败后立即重新生成不同幂等键；必须先查询任务状态。

## 8. 功能交付顺序与 Done Definition

每一个 F-xx 均需满足：API/界面可用、权限测试通过、至少一条正向与一条失败测试、结构化日志包含 request_id、数据库状态/审计一致、可通过 seed 复现。

建议顺序：F-01/F-02 → F-03/F-04 → F-05/F-06 → F-07/F-08 → F-10/F-11/F-12/F-13 → F-09/F-14。特别注意 **F-09（AI 建议）放在审批主链打通之后实现**：这是避免系统变成“AI 看似智能，但真实业务操作不可靠”的关键。
