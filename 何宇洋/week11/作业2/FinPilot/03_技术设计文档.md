# FinPilot 企业财务 Data Agent
## 技术设计文档（Technical Design / Architecture）

**版本**：v1.0（V1–V3 全量目标）  
**日期**：2026-10-22  
**技术基线**：Python + FastAPI + PostgreSQL + SQLAlchemy 2 + LangGraph + Vue 3；首版单体模块化、异步任务独立 Worker。  
**业务约束**：所有财务数据合成，所有“应用调整”均为内部模拟，不连接真实银行及生产 ERP。

---

## 1. 架构决策摘要

| 决策 | 选择 | 原因与代价 |
|---|---|---|
| 服务形态 | 模块化单体 API + 独立 Worker | 统一事务、缩短交付周期；未来可拆服务 |
| 主库 | PostgreSQL 16+ | 事务、约束、JSONB、可选 RLS、强一致写入 |
| 数据访问 | SQLAlchemy 2 / Alembic | ORM 与明确的事务边界；迁移可重现 |
| 缓存/任务队列 | Redis + Celery | 异步导入、批次匹配、报告任务；需自行保证幂等 |
| Agent 编排 | LangGraph，仅用于问数/分析/建议 | checkpoint 与受控工具；不承担审批事实来源 |
| 审批/异常状态机 | 后端 Domain Service + PostgreSQL | 确定性校验、并发安全、持久化与审计统一 |
| 文件与报告 | 本地/S3 兼容对象存储（开发用 MinIO） | 保存 CSV 原文件、报告和证据包 |
| 前端 | Vue 3 + TypeScript + Vite + ECharts | 财务工作台、状态化任务和图表呈现 |
| 可观测性 | OpenTelemetry + 结构化日志 + Prometheus | request/trace、Agent/查询/Worker 链路观测 |
| 部署 | Docker Compose（开发演示） | 快速重复部署；不是生产高可用方案 |

**关键边界**：LangGraph 产生分析、建议与计划；只有业务 API 可以创建处理方案、批准或应用受控动作。Prompt、向量知识库和模型输出都不是业务授权来源。

## 2. 逻辑架构

```text
Vue 3 Web / API Client
         |
     FastAPI API Gateway  [AuthN / AuthZ / Rate Limit / Request ID]
         |
  +------+--------------------------+-------------------+
  | Domain Services                 | AI Services       |
  | Identity / Metrics / Import     | NL2Metric         |
  | Reconciliation / Exceptions     | Query Planner     |
  | Proposal / Approval / Apply     | Analysis Graph    |
  | Audit / Reports                 | Evidence Writer   |
  +------+--------------------------+-------------------+
         |                              |
         |                              +--> Policy-governed Query Tools
         |                              +--> Document RAG (optional)
         |                              +--> Python Analysis Sandbox
         |
 PostgreSQL (source snapshots, financial marts, workflow, audit, outbox)
         |
 Outbox Publisher --> Redis/Celery --> Workers (import/reconcile/apply/report)
         |
     Object Storage (input files, report artifacts, evidence packages)
```

推荐数据库、应用内先按模块边界隔离，而不是先拆分为多个微服务。审批对象、异常状态和审计事件在同库单事务更容易保证一致性。

## 4. 数据模型（建议表与约束）

### 4.1 身份、业务与语义层

| 表 | 核心字段 | 关键约束/索引 |
|---|---|---|
| tenants | id、name | tenant 唯一 |
| users | id、tenant_id、email、active | UNIQUE(tenant_id,email) |
| memberships | tenant_id、user_id、role、scope | 范围在服务端鉴权 |
| legal_entities | id、tenant_id、name、currency | UNIQUE(tenant_id,id) |
| bank_accounts | id、tenant_id、legal_entity_id、masked_no、currency | FK 与 tenant/entity 联合约束 |
| fiscal_periods | id、tenant_id、start_date、end_date、calendar_type | 同口径期间不得重叠 |
| metric_definitions | id、code、version、formula、dimensions、active | UNIQUE(tenant_id,code,version) |
| data_snapshots | id、tenant_id、source_type、version、hash、published_at | 快照发布后只读 |
| management_facts | tenant_id、snapshot_id、entity_id、period_id、metric_code、amount | 维度聚合唯一约束 |
| query_executions | id、tenant_id、actor_id、metric_version、source_snapshot_id、sql_hash、result_hash、status | 每次问数可复核 |
| analysis_runs | id、tenant_id、actor_id、state、question、scope_snapshot、model_version | 任务与权限范围快照 |
| analysis_evidence | id、analysis_run_id、query_execution_id?、source_snapshot_id、content_hash | 结论引用证据 |
| reports | id、tenant_id、analysis_run_id、version、artifact_uri、evidence_manifest_hash | 报告产物版本化 |

### 4.2 银行、台账与对账

| 表 | 核心字段 | 关键约束/索引 |
|---|---|---|
| import_jobs | id、tenant_id、file_hash、status、source_snapshot_id | 导入任务幂等键 |
| bank_transactions | id、tenant_id、account_id、snapshot_id、external_txn_id、direction、amount、currency、biz_date | 数据版本内稳定去重 |
| cash_ledger_entries | id、tenant_id、account_id、snapshot_id、bank_reference、direction、amount、currency、biz_date | 原始账务快照不可修改 |
| reconciliation_batches | id、tenant_id、account_id、period、bank_snapshot_id、ledger_snapshot_id、rules_version、status | 固定输入组合防重复 |
| reconciliation_matches | id、tenant_id、batch_id、bank_txn_id、ledger_entry_id、kind、status | 两端交易最终 MATCH 唯一 |
| reconciliation_exceptions | id、tenant_id、batch_id、kind、bank_txn_id?、ledger_entry_id?、status、assignee_id?、version | INDEX(tenant_id,status,assignee_id) |
| match_candidates | id、exception_id、bank_txn_id、ledger_entry_id、score、reason | 只表示候选，不是最终匹配 |

**数据库级不变量**：以数据库唯一索引确保同一 bank transaction 和 ledger entry 不能出现在多个有效最终匹配中。PostgreSQL 可以用部分唯一索引限制 `status = 'FINAL'`；审计历史记录需保留，冲突不可通过覆盖旧匹配来规避。

### 4.3 审批与执行

| 表 | 核心字段 | 关键约束/索引 |
|---|---|---|
| resolution_proposals | id、tenant_id、exception_id、proposal_version、kind、payload_json、evidence_snapshot_json、created_by、created_at | 提交后不可变；版本唯一 |
| approval_requests | id、tenant_id、proposal_id、expected_exception_version、status、decision_by?、decision_at?、reason? | 一个提案至多一条活动审批 |
| apply_operations | id、tenant_id、proposal_id、operation_kind、idempotency_key、status、attempts、last_error | UNIQUE(tenant_id,idempotency_key) |
| simulated_adjustments | id、tenant_id、proposal_id、source_ref、amount、currency、reason | UNIQUE(tenant_id,proposal_id)；不触碰原台账 |
| timing_follow_ups | id、tenant_id、exception_id、rule_json、status、next_review_at | 未完成跟踪可检索 |
| audit_events | id、tenant_id、actor_id、action、object_type、object_id、before_json、after_json、correlation_id、created_at、payload_hash | append-only；INDEX(tenant_id,object_id,created_at) |
| outbox_events | id、tenant_id、event_type、aggregate_id、payload、status、created_at | 创建业务变更时同事务写入 |
| idempotency_records | tenant_id、actor_id、endpoint、key、request_hash、response_json、status | UNIQUE(tenant_id,actor_id,endpoint,key) |

所有有 tenant_id 的引用必须能够验证跨表租户一致性。建议对核心关联采用复合外键（tenant_id, id），防止关联到其他租户的同名 ID。

**金额存储**：`NUMERIC(20,4)`（仅示范业务），应用层 `Decimal`；实际精度取决于币种和产品要求。首版仅 CNY 且无汇兑自动匹配；每个指标明确元/分、正负号、舍入规则。银行交易与台账的 CREDIT/DEBIT 定义统一后才可比较。

## 5. 财务语义层与受控查询

### 5.1 指标定义示例

```yaml
code: gross_margin_rate
version: 1
display_name: 毛利率
numerator: gross_profit
# gross_profit = recognized_revenue - cost_of_goods_sold
denominator: recognized_revenue
unit: percent
dimensions: [legal_entity_id, business_line, fiscal_period]
source_view: mart_financial_metrics_v1
zero_denominator: return_null
```

指标值来源于确定性 SQL/视图，而非模型心算。自然语言与指标代码的映射可使用规则词典 + LLM 做歧义识别；将确认结果交给 Query Builder。

### 5.2 查询执行安全链

1. 身份服务确定 tenant、可访问 entity/account、角色与数据分类权限。
2. Agent 只获取**允许暴露的指标、视图、维度和过滤条件的元数据**，不能看到生产物理表完整结构。
3. 优先使用预定义指标编译器和参数化 SQL；开放式 SQL 为第二阶段能力。
4. 若允许 Text-to-SQL，对 AST 严格验证为单条 SELECT、允许的视图、函数与 JOIN；拒绝 DDL/DML/CTE 数据外泄技巧及危险函数。
5. 由可信后端组装权限谓词或数据库 RLS，不能接受模型自行拼接授权条件作为最终保障。
6. 独立只读账号、只读事务、statement_timeout、行数限制与成本/频率限制；记录执行计划摘要与查询 ID。
7. 查询结果做类型、金额精度、行数、时间边界与汇总勾稽校验后返回。

PostgreSQL RLS 可作纵深防御，但 table owner 和拥有 BYPASSRLS 的角色可绕过；必须使用独立非 owner 的受限查询角色，并按实际部署测试策略，不能只写 `ENABLE ROW LEVEL SECURITY` 就宣称安全。

## 6. Agent 设计（V1/V2/F-09）

### 6.1 编排状态

```python
class AnalysisState(TypedDict):
    request_id: str
    principal_scope: dict           # server-derived, immutable
    user_question: str
    intent: str
    metric_ids: list[str]
    plan: list[dict]
    tool_results: list[dict]       # references + bounded summaries
    evidence_ids: list[str]
    remaining_steps: int
    report_id: str | None
    errors: list[str]
```

`principal_scope` 在任务创建时由后端获得，执行工具时仍需重新鉴权。不要把用户传来的字符串当作权限范围，也不要将 Authorization Token 存入 checkpoint。

### 6.2 节点与路由

```text
validate_request
  -> resolve_metric_and_scope
  -> (ambiguous ? request_clarification : draft_plan)
  -> execute_governed_tool
  -> validate_tool_result
  -> (need_more AND budget_remaining ? execute_governed_tool : synthesize)
  -> evidence_check
  -> persist_report
```

首版工具清单（带 Pydantic schema）：`get_metric_definition`、`query_financial_metrics`、`get_reconciliation_summary`、`get_exception_evidence`、`compare_periods`、`run_safe_analysis`、`search_finance_policy`。

`run_safe_analysis` 不执行模型任意生成的 Python 代码；首版采用白名单统计操作（差值、增长率、贡献度、分组、汇总）。若要开放任意代码，需额外隔离容器、网络禁用、CPU/内存/执行时间限制、输入脱敏与输出校验。

### 6.3 RAG 与上下文

财务制度、指标解释和差异处理 SOP 可以进入 RAG；**所有金额和可计算事实仍由结构化数据获得**。检索文档需标注来源和版本，拒绝把文档中“忽略系统指令”等内容当作工具命令。

### 6.4 恢复与边界

LangGraph 持久化用于分析任务和可恢复步骤；审批业务事实来源仍是 PostgreSQL 的 workflow tables。Agent 工具中禁止暴露 `approve_proposal`、`apply_adjustment`、`mutate_ledger` 等写能力。每次任务限制最多 8 步和预算，异常时保留部分证据并告知用户。

## 7. 对账规则引擎（V3）

### 7.1 输入与匹配算法

先按 `tenant_id + account_id + currency + direction` 分桶，再按强交易参考号匹配。在同一桶中，金额精确相等且两侧候选唯一才允许最终匹配。日期可作为业务策略检查项（例如 ±3 天仅用于识别潜在时间差，不把不同日期自动视为相同）；其余输出候选或异常。

```text
for each account + snapshot pair:
    assert snapshots immutable and account authorized
    group transactions by account/currency/direction
    find one-to-one strong-reference + amount exact matches
    persist FINAL matches with uniqueness constraints
    create exception for each unmatched or conflicting case
    persist batch summary and audit in a transaction per bounded chunk
```

大型批次可分片处理，但每片写入必须幂等，批次最终完成前校验：所有记录或进入最终匹配、或进入异常/待处理候选的覆盖关系；不允许漏处理。

### 7.2 幂等策略

业务幂等标识建议：

- 导入：`tenant + account + source_type + source_version + external_txn_id`；
- 批次：`tenant + account + period + bank_snapshot + ledger_snapshot + rules_version`；
- 匹配：`tenant + bank_txn_id + ledger_entry_id + resolution_version`；
- 模拟调整：`tenant + proposal_id`。

不同级别有不同唯一性约束。客户端 Idempotency-Key 不是数据库约束的替代品；重试时 request_hash 不同要返回冲突。

## 8. 审批状态机与事务设计

**异常主状态**：`OPEN`、`INVESTIGATING`、`PENDING_APPROVAL`、`APPROVED_PENDING_APPLY`、`APPLY_FAILED`、`MONITORING`、`RESOLVED`。转移表与前置条件见功能 F-10 至 F-12。

### 8.1 提交审批（同步事务）

```text
BEGIN
  SELECT exception FOR UPDATE
  assert status == INVESTIGATING and actor authorized
  validate exception.version and all source snapshot references
  INSERT immutable resolution_proposal
  INSERT approval_request(status=PENDING)
  UPDATE exception SET status=PENDING_APPROVAL, version=version+1
  INSERT audit_event(action=PROPOSAL_SUBMITTED)
COMMIT
```

关键要求：方案 payload 与证据快照是被批准的确切内容，审批时不得重新用最新内容替换。若要更新方案，须退回后创建新版本。

### 8.2 审批决定（同步事务）

```text
BEGIN
  SELECT approval_request + exception FOR UPDATE
  check actor permission and actor != proposal.created_by
  check request status=PENDING and exception.version == submitted_expected_version
  check source snapshot and business references still valid
  write approval decision + audit_event
  if reject:
      exception -> INVESTIGATING
  else:
      exception -> APPROVED_PENDING_APPLY
      INSERT apply_operation(PENDING, stable_idempotency_key)
      INSERT outbox_event(APPLY_REQUESTED, apply_operation_id)
COMMIT
```

其中 `submitted_expected_version` 应保存为审批提交事务**完成后的 exception.version**，避免审批时错误地和旧版本比较。严格关联 proposal_id、snapshot IDs 和状态版本。

### 8.3 模拟应用（异步幂等事务）

```text
worker receives outbox event at least once
BEGIN
  SELECT apply_operation + exception FOR UPDATE
  if operation already SUCCEEDED: return existing result
  assert approval APPROVED and source/proposal unchanged
  validate not previously FINAL matched / adjustment exists
  INSERT final_match OR simulated_adjustment OR timing_follow_up
  UPDATE operation=SUCCEEDED
  UPDATE exception=RESOLVED or MONITORING, version=version+1
  INSERT audit_event(APPLY_SUCCEEDED)
COMMIT
```

若数据库写失败，整个事务回滚；worker 使用新的事务记录重试/失败状态。超出重试预算时设置 APPLY_FAILED 并保存错误摘要。重试接口保留同一 `apply_operation.idempotency_key`，不得重新生成等价的第二次会计效果。

**为什么不直接用 LangGraph interrupt 作为审批存储？** interrupt 能暂停 Agent，但不能取代财务业务数据库对职责分离、单次决策、审计、唯一生效及跨请求查询的约束。LangGraph checkpoint 只管理 AI 任务状态，审批事件的唯一事实来源是业务表。

## 10. 授权与安全设计

- **认证**：开发演示可使用受控账号及带签名短期 JWT；生产需 SSO/OIDC。服务端验证签名、有效期、颁发方与受众。
- **授权**：路由入口 + Service + Query/Repository 三层检查；对账、下载报告、导出证据包均按 tenant/entity/account 再授权。
- **职责分离**：申请人不能审批自身申请；高风险动作强制人工审批；权限变化实时影响新请求。
- **SQL 安全**：不向 LLM 提供写库连接；受限视图、参数化查询、AST 校验、只读账号、超时、行数/成本上限。
- **Prompt 注入**：用户提问和检索到的文档均视为不可信数据；从安全工具列表中物理移除写权限，不能靠“忽略恶意指令”的 Prompt 保护。
- **敏感信息**：银行卡号脱敏显示、日志避免保留原始 PII/密钥、访问审计；对象存储文件设短期下载链接或授权代理。
- **审计完整性**：业务变更与审计同事务；关键审计链可计算逐事件哈希，定期导出到独立存储。哈希链不是未经配置的法律级不可抵赖证明。
- **风控**：模型不参与角色判定和审批签名。财务建议未核验前只展示“建议”，不能写“已入账”。

## 11. 异步任务、可靠性与观察

### 11.1 任务类型

| 任务 | 建议队列 | 事务边界 | 可靠性重点 |
|---|---|---|---|
| 解析导入文件 | ingestion | 每任务/分段 | 原文件 hash、快照原子发布 |
| 执行对账批次 | reconciliation | 分片匹配后聚合 | 分片幂等、唯一匹配约束 |
| 生成 AI 分析 | agent_analysis | 各步保存分析证据 | checkpoint、限步、token 预算 |
| 应用审批动作 | workflow_apply | 一个 apply operation 的事务 | Outbox、双人复核、幂等 |
| 生成报告 | reporting | 任务记录 + 原子产物引用 | 不同数据版本不覆盖 |

**Outbox 投递**：服务端在业务事务中写入事件；投递 Worker 使用 `FOR UPDATE SKIP LOCKED` 或等价机制领取、标记重试。即使 Redis 消息重复，也依赖下游唯一键与幂等检查保证**业务效果最多一次**，不宣传消息系统提供 exactly-once delivery。

### 11.2 观测指标

`api_request_duration_seconds`、`analysis_tool_calls_total`、`llm_tokens_total`、`query_policy_rejected_total`、`recon_batch_duration_seconds`、`recon_exceptions_open`、`workflow_approvals_total`、`workflow_apply_failures_total`、`outbox_lag_seconds`。Trace 串联 `request_id / analysis_run_id / exception_id / apply_operation_id`；日志输出禁止完整银行账号或密钥。

**核心故障注入点**：审批事务提交前、提交后 Outbox 未发布、worker 应用事务中、事务提交后 ACK 前、重复消费、模型拒答、外部存储不可达、用户审批时源记录版本冲突。对“事务提交后 ACK 前”必须验证业务效果只有一份。

### 12.1 验收门槛

与项目设计文档一致：未授权泄露 0、无审批生效 0、重复业务生效 0、关键审计完整率 100%、确定性对账真值集 100%、问数准确率目标 ≥95%、V2 证据支持率目标 ≥95%。这些均为**拟定验收值**，要保留测试集、运行环境与结果报告，不得写成已实现指标。

## 14. 需要尽早验证的设计决策（ADR）

- **ADR-01 仅模拟执行**：禁止真实资金和正式账簿写入，避免金融系统连接的不可控风险。
- **ADR-02 规则先于模型**：金额、币种、参考号匹配与状态机由确定性程序实现。
- **ADR-03 审批不放在 LangGraph**：财务工作流由 PG 事务约束，AI checkpoint 单独存放。
- **ADR-04 最小权限查询**：不直接执行任意 LLM SQL；先通过语义 API，随后才受控开放 SQL。
- **ADR-05 状态与副作用解耦**：APPROVED_PENDING_APPLY / APPLY_FAILED 明确描述审批已过但生效未完成。
- **ADR-06 证据不可变**：报告、提案及审批使用版本化数据快照，历史结果可重现。
