# FinPilot 企业财务 Data Agent
## 项目设计文档（Project Design / PRD）

**版本**：v1.0（目标版本 V3）  
**日期**：2026-10-22  
**项目性质**：可演示、可验收的企业财务智能分析与银行对账工作流平台  
**重要声明**：首版仅使用合成数据、模拟 ERP/银行流水；不连接真实账户，不执行真实转账、付款、法定记账或税务申报。

---

## 1. 项目摘要

FinPilot 是面向中小型企业财务团队的业务系统，提供自然语言财务问数、交互式经营分析、银行流水与内部资金台账对账、异常工单、双人复核审批和完整审计链。以“可核验的数据结果 + 受控的业务动作”为基本原则，将 ChatBI（V1）、分析型 Data Agent（V2）与财务 Workflow Agent（V3）整合在同一平台。

**核心业务闭环**：导入账务及银行流水 → 统一数据口径 → 财务问数/异常定位 → 规则对账并发现差异 → AI 生成差异解释和处理建议 → 经办人提交处理方案 → 独立审批人复核 → 后端应用受控的模拟处理动作 → 留存证据、状态与审计记录。

**产品定位**：业务侧财务分析与异常处理助手；不是通用 ERP、自动记账系统、真实银行交易系统或投资建议产品。

## 2. 背景与待解决问题

企业财务团队常见的割裂流程是：财务人员需要向数据团队提出指标需求；经营数据与账务数据在不同系统；对账异常通过电子表格和聊天记录处理；异常原因、审批过程和最终处理结果缺乏统一证据链。

平台要解决的四个问题：

1. **查数成本高**：自然语言问题难以对应财务指标、时间边界与组织范围。
2. **分析过程不可追溯**：自动生成的结论缺少 SQL、数据版本、指标定义与证据。
3. **异常处理链断裂**：对账工具发现差异后，无法直接分派、处理、审批与跟踪。
4. **操作风险不可控**：权限控制、双人复核、幂等与审计往往是后补机制。

## 3. 目标用户、职责与权限边界

| 角色 | 核心任务 | 可访问范围 | 明确限制 |
|---|---|---|---|
| 财务分析师（ANALYST） | 问数、分析、报告、查看允许的对账结果 | 授权组织/法人主体/账户 | 不可审批或执行处理动作 |
| 财务经办人（OPERATOR） | 导入文件、领取异常、提交处理方案 | 授权主体和银行账户 | 不可审批本人提交的申请 |
| 财务审批人（APPROVER） | 查看证据、批准/驳回异常处理申请 | 授权审批范围 | 不得批准本人发起的申请 |
| 财务主管（MANAGER） | 查看团队任务、审计汇总、报告和规则配置 | 管理范围内的主体 | 规则变更需留痕；不等于超级用户 |
| 系统管理员（ADMIN） | 管理租户成员、角色、接入与系统配置 | 管理平面 | 不因系统管理员身份自动取得所有财务数据的业务可见性 |
| 审计员（AUDITOR） | 只读查看关键操作及证据链 | 授权审计范围 | 不得修改业务单据及审计日志 |

**权限模型**：RBAC（角色）+ ABAC（tenant_id、legal_entity_id、account_id、数据分类、金额权限）；身份与权限在后端工具/API 层执行，不依赖 LLM 提示词。默认一名用户可拥有多个角色，但经办与审批实行同一业务请求的人员分离。

## 4. 产品目标及不做的事情

### 4.1 目标

- O1：让授权用户通过自然语言获得**口径明确且可复核**的财务指标、趋势和明细。
- O2：让用户对经营与财务差异开展多步骤分析，生成关联数据、结论和报告。
- O3：实现银行流水与企业资金台账的对账、异常认领、处理申请、独立审批、模拟生效、审计闭环。
- O4：在完整链路中具备租户隔离、幂等、故障恢复、操作留痕和可量化评测。

### 4.2 非目标

- 不面向证券交易、信贷授信、投资推荐或量化交易；不实现外汇实时行情。
- 不直连真实银行账户、不代替持牌支付能力；不发起真实付款或划款。
- 首版不实现法定会计账簿过账、税务申报、跨境合规、复杂合并抵销及正式财务报表审计。
- 不以“LLM 自动决定审批结果”替代人工复核；模型只能给建议、不能签署审批。
- 不做全行业通用 Text-to-SQL；只覆盖明确登记的财务语义模型及授权数据集。

## 5. 核心业务场景

### 5.1 财务问数（V1）

“2026 年 Q3 华东业务的已确认收入、营业成本和毛利率分别是多少？和 Q2 相比怎样？”

系统解析指标、币种、会计期间与主体；调用已注册指标或受限查询模板；返回可复核的数值、图表、口径与数据来源。遇到“利润”等歧义指标应澄清，不擅自推断。

### 5.2 多步财务分析（V2）

“本季度净利润下降的主要贡献项目有哪些？按业务线与费用类别下钻，并给出证据。”

系统先做会计报表项目变化分解，再查询业务线、费用维度和经营背景，明确“变动贡献”和“根本原因”的区别，输出结论、证据和待验证假设。

### 5.3 银企对账与异常闭环（V3）

“导入 9 月某账户的银行流水，与 ERP 模拟资金台账自动对账，查出未匹配项；对于一条疑似重复付款记录，发起人工复核；处理结果可回溯。”

自动匹配只覆盖明确、唯一、确定的情形；模糊匹配和 AI 建议不能直接使账务生效。业务审批通过后由确定性后端完成模拟匹配标记或模拟调整记录，并发出成功/失败事件。

## 6. 版本范围与依赖关系

| 版本 | 交付边界 | 必须可演示的结果 | 关键依赖 |
|---|---|---|---|
| V1 · ChatBI | 财务语义层、权限查询、指标趋势、基础图表 | 用户问数 → 可复核 SQL/指标结果与证据 | 财务模型、数据集、租户隔离 |
| V2 · Analysis Agent | 多步分析计划、工具调用、下钻、报告与评测 | 复杂问题 → 多次查询 → 证据支持的报告 | V1 + 分析执行与评测框架 |
| V3 · Workflow Agent | 对账、异常台账、领取分派、处理方案、审批、模拟执行、审计 | 差异产生 → 工单 → 人工审批 → 模拟生效 → 审计闭环 | V1/V2 + 事务性业务后端 |

首个可交付目标按 V3 规划，但推荐按以上顺序分阶段验收。V3 的审批与对账服务不依赖 LLM 在线可用：模型不可用时，财务工作流仍应运行。

## 7. 数据场景及模拟平台设计

**数据域**：租户/主体/部门、科目表与财务期间、总账与管理口径汇总、销售订单/发票、内部资金台账、银行流水、预算、对账批次及匹配关系、异常、审批、审计、知识文档。

**合成数据原则**：使用确定性 seed 生成相互关联的记录，固定基准期、主体、账户与币种；数据要能在报表、台账与银行流水之间交叉核验；必须明确人为植入异常的真值标签。

**至少覆盖以下异常**：银行有账/内部无账、内部有账/银行无账、金额不一致、交易参考号重复、日期跨期、手续费差额、多候选匹配、人工已处理后重复提交、审批过程中数据被其他任务修改、外部模拟回写失败。

模拟数据需要含有正常业务与脏数据，避免仅生成随机数后让 LLM 自行解释。提供“重置到指定 seed”的一键环境初始化能力。

## 8. 核心使用路径（用户故事）

| 编号 | 用户故事 | 成功标准 |
|---|---|---|
| US-01 | 分析师查询收入和毛利率 | 能看到口径、数据时间与证据；跨租户不得返回 |
| US-02 | 经理追问费用异常 | 系统明确下钻路径、数据支持程度和报告链接 |
| US-03 | 经办人上传银行流水 | 能校验格式、重复导入、金额和账户权限 |
| US-04 | 经办人启动对账 | 对账批次可追踪、可重试且不重复产生匹配 |
| US-05 | 经办人认领并提交异常方案 | 保存证据、版本与审批对象，禁止重复提交 |
| US-06 | 审批人审查处理方案 | 不能审批自己的申请；拒绝需理由，操作有审计 |
| US-07 | 审批通过后执行模拟调整 | 应用操作幂等、失败可重试、状态准确 |
| US-08 | 审计员追溯一次异常 | 可串起原始数据、建议、人工操作、审批、执行事件 |

## 9. 关键业务规则

1. 原始银行流水和内部资金台账**不可因模型输出而直接修改**；对账匹配关系与模拟调整必须单独建模。
2. 币种不一致不自动匹配；不存在未经指定汇率来源的跨币种折算。
3. 精确匹配要求账户、币种、方向、金额与唯一的交易参考号（或确定性外部 ID）一致；不满足唯一性就转为候选。
4. AI 可解释差异、推荐处理类型和理由，但不能批准自己的建议，更不能绕过审批调用写接口。
5. 经办/审批人与权限范围基于后端真实身份判断；同一申请禁止自己审批。
6. 审批处理的标的在提交时绑定版本和证据快照；发生数据变更必须阻止过期审批。
7. 所有状态变化要求合法前置状态、乐观锁版本与幂等键；审计日志与业务提交在同一事务中落库。
8. 审批成功不等于执行完成；异步模拟生效成功后才能标记 RESOLVED；失败进入 APPLY_FAILED。
9. 时间性差异可以进入 MONITORING，等待下一批次重新验证；不能当作已核销。

## 10. 非功能目标与验收阈值（目标值，非现有实测）

| 指标 | 建议目标/硬门槛 | 测量方式 |
|---|---|---|
| 未授权数据泄露 | 0（硬门槛） | 跨租户/跨账户越权测试集 |
| 核心对账确定性规则 | 正确率 100%（合成真值集） | 离线 fixture 比对 |
| 禁止无审批直接生效 | 0（硬门槛） | API、工具调用与故障注入测试 |
| 重复请求导致重复处理 | 0（硬门槛） | 并发、超时、重放测试 |
| 关键写操作审计完整度 | 100%（硬门槛） | 审计日志与业务事件核对 |
| V1 指标答案准确率 | ≥95%（限定评测集） | 固定问题集，与确定性 SQL 真值比对 |
| V2 证据支持率 | ≥95%（限定评测集） | 人工标注 + 自动核验 |
| 基础指标查询接口 P95 | ≤2s（本地部署演示目标） | 固定数据规模压测；不含外部 LLM |
| 完整分析报告耗时 | 单独报告，不预设硬实时 SLA | 统计 P50/P95、tokens 与费用 |

涉及财务安全的门槛只接受测试通过，不以平均正确率替代。目标值须与测试环境、数据量、并发数同时报告。

## 12. 风险与取舍

| 风险 | 后果 | 处理策略 |
|---|---|---|
| 财务术语和口径歧义 | 数字正确但答非所问 | 指标字典 + 歧义澄清 + 版本管理 |
| LLM 编造原因 | 管理决策失真 | 将事实/贡献/假设分开，结论绑定证据 |
| 低质量模拟数据 | 项目缺乏可信业务闭环 | 确定性场景生成器 + 异常真值 |
| 多模块过度开发 | 无法形成可演示成品 | 先 1 个业务主体、2 个账户、1 条完整审批链 |
| 并发及重试造成重复应用 | 重复记账/状态混乱 | 乐观锁 + 唯一键 + Outbox + 幂等 |
| 权限依赖 Prompt | 越权查询/写入 | 数据访问层强制鉴权和范围限制 |
| 模型服务不可用 | 业务阻断 | 决策建议降级；对账与审批独立运行 |

## 13. 验收演示脚本

1. 初始化 `demo-seed-2026q3`：包含 2 个主体、2 个银行账户、季度财务数据及预设异常。
2. 以分析师登录，问“Q3 毛利率环比变化”，查看指标口径、查询证据和图表。
3. 提问“哪一项成本贡献最大”，由 V2 多步查询输出带引用的分析报告。
4. 以经办人导入 9 月银行流水，发起对账，展示精确匹配、候选匹配及异常。
5. 领取一条“内部缺账”异常，AI 解释原因并给出建议；经办人选择“模拟调整”并提交审批。
6. 使用同一经办人尝试审批，系统拒绝并记录安全事件。
7. 以审批人身份批准，触发异步模拟应用；刷新至 RESOLVED，并出现唯一调整记录。
8. 重放审批/应用请求，确认不重复生效；故障注入后验证 APPLY_FAILED 与重试恢复。
9. 审计员导出异常时间线，能看到源记录、证据快照、模型建议、经办人、审批决定及执行事件。

## 14. 术语与引用

- **对账批次**：一次针对给定账户/期间/数据版本的确定性匹配运行。
- **异常工单**：对账过程中生成、需要人工处理或后续跟踪的差异对象。
- **审批请求**：对一份不可变处理方案快照发起的复核动作。
- **模拟调整**：平台内的演示记录，不向银行或正式 ERP 账簿过账。
- **分析证据**：带数据源、指标口径、查询版本与时间戳的结构化结果。
