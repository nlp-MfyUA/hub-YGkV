## 1. 项目背景

### 1.1 业务现状

企业里的数据需求呈现明显的「二八分布」：

- 20% 的固定报表，已经由 BI 平台 / 数仓看板覆盖；
- 80% 是临时、零散、追问式的取数需求——"上个月华东区的 GMV 是多少""这几个渠道的转化率对比一下""为什么 9 月销量掉了"。

这 80% 需求目前的三条路径都不理想：

| 路径 | 问题 |
| --- | --- |
| 业务自己写 SQL | 门槛高，绝大多数业务人员不具备 |
| 提需求给数据团队 | 排期长（常见 3~7 天），业务等不起，临时需求还会挤占数据团队的建模工作 |
| 拖拽式 BI 工具 | 需要预先建模、配置图表和公式，只适合已知问题，不适合探索式提问 |

### 1.2 技术背景

两类能力同时成熟，使 ChatBI 从"演示品"走向"可用产品"成为可能：

1. **大模型的语义理解与工具调用能力**：可以把自然语言翻译成 SQL、选择工具、总结结果；
2. **Agent 工程化框架**（OpenAI Agents SDK、MCP、LangGraph 等）：把"理解 → 检索 → 生成 → 校验 → 执行 → 汇总"拆成可编排、可观测、可替换的流水线。

但需要清醒地认识到：**这个产品的难点不在"大模型会不会写 SQL"，而在"写出来的 SQL 敢不敢用"**。一次错误的数字，代价远大于一次交互不顺畅。

### 1.3 行业参考

| 企业 | 落地路径 | 共性 |
| --- | --- | --- |
| 去哪儿网 | 字段整理 → SQL Agent → 多 Agent（生成 + 优化）→ ReAct → 反问与路由 → RAG 注入 | 逐步拆分职责，先保证正确再谈智能 |
| 腾讯游戏 | 字段整理 → 需求拆解 → 历史知识检索 → SQL 生成与验证 → 执行与可视化 | 检索与验证是关键环节 |
| 网易 | 字段整理 → 需求拆解 → 逻辑 SQL / 物理 SQL → 人工参与 | 复杂场景允许人工兜底 |
| FreeWheel | 字段整理 → 关键字检索与智能选表 → SQL 生成与优化 → 可视化 | 选表是准确率的分水岭 |

四个案例的第一步都是"数据字段整理"——这说明**语义层的价值高于模型本身的调优**。

## 2. 项目目标

### 2.1 业务目标

1. 把业务人员的临时取数周期从 **天级缩短到分钟级**；
2. 让数据团队从临时取数中解放出来，聚焦建模与治理；
3. 让业务口径**可沉淀、可复用、可审计**，减少"同一个指标三个数"的情况。

### 2.2 产品目标（可度量）

| 目标 | 衡量方式 | 一期目标 |
| --- | --- | --- |
| 答得准 | Golden Set 结果集一致率 | ≥ 85% |
| 问得到 | 一次通过率 | ≥ 75% |
| 敢采用 | 试点用户采纳率 | ≥ 50% |
| 不越权 | 危险 / 越权 SQL 拦截率 | 100% |
| 出结果快 | 端到端响应 P90 | < 10s |

### 2.3 非目标（一期明确不做）

明确"不做什么"比"做什么"更重要，以下内容一期不做，避免范围失控：

- **不做全库自由查询**：只覆盖经过治理的核心指标与数据表；
- **不做因果归因**：不做"为什么下降"的因果推断，只做基于查询结果的事实描述；
- **不做主动洞察与订阅推送**：异常检测、指标预警后置，准确率不达标时推送只会变成噪音；
- **不做多数据源适配**：一期只接一个数仓；
- **不做自助建模**：语义层由数据团队维护，业务侧只消费；
- **不替代固定报表**：固定报表继续由现有 BI 承载。

## 3. 目标用户与典型场景

### 3.1 用户角色

| 角色 | 关注点 | 典型提问 |
| --- | --- | --- |
| 业务分析师 | 快速验证假设、探索数据 | "近 30 天各渠道的新增用户数，按天拆" |
| 运营 | 活动效果、转化漏斗 | "本次活动的下单转化率，和上期比怎么样" |
| 业务管理者 | 核心指标、趋势 | "本季度各区域的 GMV 排名前 5" |
| 数据团队 | 口径治理、审计 | "哪些指标被问得最多、哪些问题答错了" |
| 系统管理员 | 权限、合规 | "谁在什么时候查过客户明细" |

### 3.2 典型场景（用户故事）

**场景 A：单指标查询（最高频）**

> 运营小李想知道"昨天华东区的订单量"。
> 系统识别指标=订单量、维度=区域、过滤=华东、时间=昨天，生成 SQL 并执行，
> 返回指标卡 + 一句结论："昨天华东区订单量 12,480 单，环比下降 3.2%。"

**场景 B：多维度对比**

> 分析师问"最近 4 周，各渠道的注册转化率对比"。
> 系统输出折线图（时间 × 转化率，按渠道分系列），并标注数据新鲜度。

**场景 C：口径歧义**

> 用户问"转化率是多少"。
> 系统检索到"注册转化率""下单转化率""支付转化率"三个候选，
> 以选择题形式反问，而不是默认选一个。

**场景 D：多轮追问**

> "看下 Q3 的销售额" → "按产品线拆" → "只看华东" → "和去年比"。
> 系统维护结构化会话状态，逐轮增量修改，而不是把历史全塞进提示词。

**场景 E：超出能力边界**

> 用户问"为什么上个月销量跌了"。
> 系统识别为归因类问题，明确告知"我擅长查询与对比，归因分析建议结合业务背景判断"，
> 并给出可执行的替代问法（拆分维度、对比同期），而不是硬生成一条 SQL。

**场景 F：越权访问**

> 区域经理问"全公司的薪酬数据"。
> 系统在检索阶段就不召回未授权的指标，明确提示无权限，并记录审计日志。

## 4. 产品形态与范围

### 4.1 产品形态

- **对话式工作台（Web）**：主入口，聊天 + 结果表格 + 图表 + SQL 可折叠展示；
- **嵌入式组件**（二期）：以 iframe / SDK 形式嵌入现有业务系统；
- **管理后台**：语义层管理、权限配置、审计查询、质量看板。

### 4.2 一期范围（MVP）

```
✅ 单轮 + 多轮自然语言问数（覆盖 30~50 个核心指标）
✅ 指标级 / 行级 / 列级权限
✅ SQL 展示、口径说明、数据新鲜度
✅ 指标卡 / 柱状 / 折线 / 饼图 四类基础图表
✅ 结果结论生成（同比/环比/TopN 的事实描述）
✅ 反馈（采纳 / 不对）与 bad case 沉淀
✅ 审计日志
❌ 主动洞察、订阅推送、多数据源、自助建模、归因分析
```

### 4.3 核心能力分级

参考调研结论，能力按"敢用 → 能用 → 好用"分级：

| 优先级 | 能力 | 解决什么问题 |
| --- | --- | --- |
| **P0** | 语义层 / 指标口径治理 | 让"GMV""销售额"有唯一、机器可读的定义，是准确率的上限 |
| **P0** | 可信度与可解释性 | 展示 SQL、口径、数据来源与新鲜度，让业务敢用 |
| **P0** | 权限与数据安全 | 行列级权限在 SQL 层强制，避免越权与泄露 |
| **P1** | 自然语言转 SQL（含消歧） | 把口语问题转成正确查询，难点在消歧而非语法 |
| **P1** | 图表自动选型 + 结论生成 | 用户要的是洞察，不是结果表格 |
| **P1** | 多轮对话与上下文管理 | 真实分析是迭代的，支持增量修改 |
| **P2** | 查询性能与成本控制 | 防止一条 SQL 拖垮数仓 |
| **P2** | 反馈闭环与持续优化 | 准确率靠运营提升，不是一次性调优 |
| **P2** | 主动洞察与订阅 | 从"人问"到"系统报"，依赖前面能力的准确率基础 |

> 关键判断：很多团队一上来猛攻 NL2SQL 模型效果，却忽略语义层和权限，
> 结果"演示惊艳、上线即死"。**语义层 + 可信度 + 权限是地基。**

## 5. 成功指标

### 5.1 北极星指标

**周活跃提问用户数 × 采纳率**：既反映使用广度，也反映结果可信度。只看提问量会鼓励"为了问而问"，只看采纳率会被小样本误导。

### 5.2 分层指标

| 层次 | 指标 | 一期目标 |
| --- | --- | --- |
| 准确性 | Golden Set 结果集一致率 | ≥ 85% |
| 准确性 | 一次通过率 / 澄清后通过率 | ≥ 75% / ≥ 90% |
| 准确性 | 兜底率（走 LLM 自由生成的比例） | < 10% |
| 安全 | 越权 / 危险 SQL 拦截率 | 100%（硬指标） |
| 安全 | 审计覆盖率 | 100% |
| 体验 | 端到端 P90 响应时长 | < 10s |
| 体验 | 报错率（点"答案不对"） | < 15% |
| 价值 | 试点用户采纳率 | ≥ 50% |
| 价值 | 人工取数工单量下降 | ≥ 50% |

## 6. 迭代路线（3 人团队，3 个月）

团队构成：1 后端 + 1 算法 + 1 前端。核心策略是**先做"可信的窄场景"（30~50 个核心指标），而不是"不可信的宽场景"（全库自由查询）**。

| 阶段 | 时间 | 主题 | 里程碑 |
| --- | --- | --- | --- |
| M1 | 第 1~4 周 | 地基：语义层 + 安全权限 + 最小闭环 | 20 个核心指标可问，结果可信、权限正确 |
| M2 | 第 5~8 周 | 可用：准确率 + 图表 + 多轮 | 10 人内测，一次通过率 ≥ 60% |
| M3 | 第 9~12 周 | 可信与规模化：评测闭环 + 质量 + 试点 | 30 人试点，一致率 ≥ 85% |

### 6.1 M1：地基与最小闭环

**目标**：跑通"提问 → 语义层编译 SQL → 权限注入 → 执行 → 出结果"的端到端链路。

| 角色 | 主要工作 |
| --- | --- |
| 后端 | 语义层存储与编译器（YAML → IR → SQL）；只读账号与资源隔离；超时熔断；RLS 注入；审计表；SQL 静态拦截 5 条规则 |
| 算法 | 意图分类 + 槽位抽取（时间解析用确定性规则）；指标检索（向量 + 别名）；多候选指标澄清 |
| 前端 | 对话界面；结果表格；指标卡/柱状/折线三类图表；SQL 与口径可折叠展示；澄清选项交互 |

**里程碑验收**：20 个指标可问；两个区域账号问同一问题 SQL 自动带不同 `WHERE`；50 条危险 SQL 全部拦截。

**风险预警**：不要一开始就做多表复杂 JOIN；语义层 YAML 结构第一版必须定好，后期改动成本极高。

### 6.2 M2：准确率与体验

**目标**：一次通过率从"能跑"到"能用"，10 人内测。

| 角色 | 主要工作 |
| --- | --- |
| 算法 | 150 条 Golden Set；few-shot 示例库；多轮结构化状态；结果自检规则 |
| 后端 | 多表 JOIN 与聚合去重（防一对多重复计数）；查询缓存；数据新鲜度检查；执行失败回退（上限 2 次） |
| 前端 | 图表规则化选型；结论展示；空结果区分提示；反馈按钮 |

**里程碑验收**：Golden Set 一致率 ≥ 75%；一次通过率 ≥ 60%；澄清后通过率 ≥ 80%；兜底率 < 20%。

### 6.3 M3：可信、质量与试点

**目标**：30 人试点，建立持续优化机制。

| 角色 | 主要工作 |
| --- | --- |
| 算法 | bad case 周度归因（口径缺失 / 表选错 / 歧义未澄清 / 数据问题）；回归评测；Top 失败模式专项优化 |
| 后端 | 数据质量看板；成本可观测；审计查询接口；慢查询降级 |
| 前端 | 在线指标看板；试点引导；能力边界说明 |

**里程碑验收**：一致率 ≥ 85%；30 人试点、周活跃 ≥ 15 人、采纳率 ≥ 50%；回归机制上线；安全合规检查通过。

### 6.4 能力排期说明

| 能力 | 阶段 | 理由 |
| --- | --- | --- |
| 业务口径知识注入（RAG） | M1 最小版，M2 完善 | 准确率的地基；晚做等于前面的测试白做 |
| 歧义澄清反问 | M1 最小版，M2 系统化 | 多义指标必然存在，默认选一个会静默答错 |
| 多轮对话 | M2 | 单轮不准时，多轮只会放大错误 |
| 图表生成 | M1 基础版，M2 规则化 | 成本低、感知强，早做早验证 |

## 8. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 语义层覆盖不足导致准确率低 | 用户不信任，产品失败 | 一期只覆盖 Top 30~50 指标；语义层优先于模型调优 |
| 大模型生成错误 SQL 但能执行 | 错误数字被用于决策 | 结果自检 + 口径回显 + 低置信度提示；宁可说不会 |
| 越权访问 | 合规事故 | 权限在 SQL 层注入；只读账号；审计；拦截率作为硬指标 |
| 查询拖垮数仓 | 生产事故 | 资源组隔离、超时熔断、行数上限、分区过滤校验 |
| 业务口径争议 | 数字对不上 | 指标 owner 制；口径变更走评审；对账机制 |
| 范围失控 | 3 个月做不完 | 明确非目标；每个里程碑只做约定范围 |
