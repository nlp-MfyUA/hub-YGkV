# Markdown 报告结构与质量验收

## 正文

1. **标题与本月关键判断**：客户、月份、研究截止时间。先说明值得技术人员行动的变化、优先级和关键未知条件；没有重要更新就如实表达，不用旧闻补量。
2. **研究范围**：主体、业务、地区、报告期 `[start,end)`、日期纳入规则、同行选择理由。区别本期事实和历史基线。
3. **政策、评级与标准**：每条包含已核验变化、来源、状态/版本、适用性、时点和技术数据要求。三个子项均需有检索结果；无更新和访问失败分别写清楚。
4. **公司动态及技术影响**：把原始事件与资产/业务或数据能力连接，解释因果链及不确定性。集团事件标明是否影响上市公司及其依据。
5. **行业与对标实践**：明确同行业务、做法、披露成果与证据；解释可迁移条件、工程或运行约束及验证方法。
6. **行动清单**：建议动作、优先级、建议责任职能、交付物、验证指标及依赖条件。期限按事实紧迫性确定；未知现状先核实/评估。技术方案须考虑运营、人员、维护和披露的后续影响。
7. **来源与缺口**：核心事实证据表、额外背景及未核实线索、查询/来源覆盖和失败来源。链接完整台账，保持可复核。

长段落拆成可以审阅的事实与分析。表格用于政策比较、同行和行动；必要解释放正文，避免每格塞入长文章。图表仅在数据、边界和比较口径可信且有助判断时生成；不因追求效果增加装饰图或无依据评分。

## 引用

使用标准 Markdown 引用链接，在事实附近写 `[C001]`，底部定义为原文 URL：

```markdown
该规则的发布与生效安排见正式文件 [C001]。针对客户的适用性仍需核实具体主体分类。

| 事实 ID | 来源与原文位置 | 事实及口径 |
| --- | --- | --- |
| C001 | [发布机构正式文件](https://example.org/document)，第 3 条 | 已核实事实；发布日期、生效日期分别记录 |

[C001]: https://example.org/document "发布机构、标题、日期"
```

示例 URL 仅说明格式，真实报告必须替换为核实过的原文。一个事实有多个来源时，定义指向主来源，证据表与台账保留其他来源。未核实/冲突的线索使用直接来源链接并标注状态，不作为已核验事实引用。可以筛选候选事实，不必把台账中全部已核实事实塞进正文。

## 交付前复核

- 对高影响政策逐条核对正式稿、版本、日期、主体和过渡安排；对关键数字核对单位、统计期、边界和方法。
- 检查“事实—影响—动作”因果链。推断须显式表达，不能假装来源提出了本报告自己的结论。
- 检查每个行动是否有触发事实、可检查的交付物和未知前提；不得虚构客户内部缺陷、负责人、成本或现有技术能力。
- 检查同行的业务可比性与指标口径；负面事件、反证和证据缺口不能因影响报告观感而删除。
- 运行证据校验，打开报告检查标题、引用、表格和路径；程序通过只代表有限结构检查通过。
- 汇报生成报告与证据台账的绝对路径、重要发现、覆盖限制和投递状态。完整内容保存在本地，机器人只发适合渠道的摘要。
