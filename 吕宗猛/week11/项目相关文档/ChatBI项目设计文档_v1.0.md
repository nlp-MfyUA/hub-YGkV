# ChatBI 项目设计文档

-   **版本**：初稿 v0.1
-   **状态**：需求与架构初稿，待业务及安全评审
-   **项目类型**：企业内部自然语言数据查询平台
-   **部署倾向**：Docker Compose
-   **数据源**：单个 MySQL 数据库，约 20--100 张表
-   **用户规模**：约 10--50 人

> 标记约定：**【已确认】**表示用户已明确提出；**【暂定方案】**表示本初稿的建议；**【待决策】**表示仍需业务、安全或技术评审确认。

## 1. 项目概述

### 1.1 项目背景

企业现有业务数据存储于
MySQL，涉及多个业务模块。传统查询依赖用户理解数据库结构、业务字段及 SQL
语法，业务人员获取数据的门槛较高。项目拟提供自然语言问数能力：用户用自然语言提出问题，系统生成
SQL，在安全校验及权限控制后执行查询，再以自然语言、表格和图表返回结果。

### 1.2 项目目标

1.  支持业务人员通过自然语言查询现有业务数据。
2.  支持常见过滤、排序、分组、聚合和受控多表关联。
3.  强制执行表级、字段级、行级权限。
4.  支持多轮追问，并在修改条件时保留正确上下文。
5.  控制生产数据库的查询耗时、返回行数、并发和资源消耗。
6.  提供查询历史、授权共享、审计和错误追踪。
7.  第一版仅查询，不修改生产业务数据。

### 1.3 项目范围

**第一版范围** - 用户登录及用户、部门、角色管理。 -
数据库元数据采集和业务语义配置。 - 自然语言问题理解、相关 Schema 检索和
SQL 生成。 - SQL 程序化校验、权限校验、只读执行。 -
查询结果处理、脱敏、自然语言回答、表格和图表。 - SQL
供后台审计；普通用户不展示 SQL。 -
多轮追问、上下文修正、个人历史及授权共享。 -
查询超时、结果集限制、并发控制、错误日志和审计日志。 - Docker Compose
部署。

**暂不纳入第一版** - 数据写入、更新、删除和 DDL。 - 任意 SQL
编辑器或可直接执行用户自定义 SQL 的控制台。 - 多数据源及跨数据库查询。 -
自动导出和其他数据操作；后续单独设计权限与审计。 -
未经确认的复杂预测、因果分析或自动化业务操作。

## 2. 需求基线

### 2.1 已确认需求

  项目         已确认内容
  ------------ ----------------------------------------
  业务场景     查询现有业务系统数据
  数据库       单个 MySQL 数据库，多业务模块
  数据规模     约 20--100 张表
  模型         云端 API
  用户规模     约 10--50 人
  身份管理     需要新建用户权限管理
  组织关系     用户通常属于单一部门、通常只有一个角色
  权限         模块/表级、字段级、行级
  行级范围     本人及所属部门
  敏感数据     按权限脱敏
  数据库连接   生产 MySQL，但只提供只读用户
  SQL 展示     普通用户不展示 SQL
  会话         支持多轮追问及上下文纠正
  历史         个人历史及授权共享
  错误处理     有限次数自动修正
  查询限制     严格限制执行时间、结果行数和并发
  展示         自然语言、表格、图表、历史
  部署         优先 Docker Compose
  Schema       表结构和字段注释较完整
  未来方向     可能支持导出或其他数据操作

### 2.2 主要暂定方案

1.  第一版仅开放经后端校验的只读查询。
2.  大模型只生成候选 SQL，不负责决定权限是否允许。
3.  所有查询均绑定当前登录用户身份；每次执行时重新加载或验证有效权限。
4.  默认不把原始敏感查询结果直接发送给云端模型。
5.  使用独立的查询执行组件与受限数据库账号，设置硬性超时、行数和并发限制。
6.  保存结构化会话上下文，而不是只依赖聊天文本。
7.  通过业务元数据配置表关系、业务术语、指标口径和权限字段映射。
8.  自动修正只针对有限次数的可恢复错误，每次修正后的 SQL
    都必须重新经过完整校验。

### 2.3 待决策事项

-   云端模型供应商、模型型号、API 区域、数据处理条款和保留策略。
-   是否有只读副本；若只有生产主库，需进行负载评估并确认允许的查询窗口。
-   行级权限在各业务表中的具体关联字段和规则。
-   敏感字段清单、脱敏方式，以及敏感值是否允许进入模型上下文。
-   业务指标口径、状态字典、软删除条件和默认时间范围。
-   认证方式、密码策略、是否需要验证码或企业 SSO。
-   查询历史保留周期、共享授权流程和审计人员范围。
-   初始超时、最大返回行数、并发数、修正次数和速率限制。
-   是否需要数据导出、Excel 下载及相关授权。
-   第一版验收数据集、准确率目标和性能目标。

## 3. 用户角色与权限模型

### 3.1 暂定角色

  角色         建议职责
  ------------ --------------------------------------------
  系统管理员   用户、部门、角色、系统配置管理
  权限管理员   业务模块、表、字段、数据范围及脱敏规则配置
  普通用户     提交查询、查看本人授权结果、管理个人历史
  审计人员     在授权范围内查看查询审计和安全事件

角色名称和职责是建议，并非已确认组织安排。系统管理员与权限管理员是否分离，需要安全评审。

### 3.2 权限维度

**表级权限**：控制用户可访问的业务模块、表及允许的关联路径。

**字段级权限**：至少区分： - 是否允许读取字段； -
是否允许将字段用作过滤、分组、排序或 JOIN 条件； - 是否允许展示原值； -
是否允许将字段值发送给云端模型。

仅隐藏前端列不构成字段权限控制。即使字段不显示，也应防止通过筛选、排序、聚合或错误信息间接泄露其值。

**行级权限**：将查询限制为本人及所属部门的数据。具体规则按业务表配置，不假设所有表都具有相同的用户或部门字段。

**共享权限**：共享查询历史不自动授予原始数据访问权。共享者再次查看结果时，应验证其当前权限；如权限不足，应隐藏或重新执行查询，不能直接暴露历史快照。

### 3.3 权限执行原则

1.  用户身份由服务端认证上下文确定，不从用户输入或模型输出中获取。
2.  权限校验发生在 SQL 执行前，并覆盖 JOIN、子查询、聚合和多轮追问。
3.  查询结果返回前再次执行字段过滤和脱敏。
4.  每次执行均使用当前有效权限；不能沿用会话创建时的旧权限。
5.  权限配置变更、失败访问和管理员操作需要审计。
6.  对无法可靠应用行级规则的表，默认拒绝自然语言查询，直到规则经过验证。

**重要风险**：MySQL
只读账号只能限制写入，通常不能自动限制某用户只能看到本人或本部门的记录。因此必须另有可靠的行级权限实施机制。

## 5. 核心业务流程

### 5.1 自然语言查询主流程

1.  用户登录并提交自然语言问题。
2.  服务端获取用户身份、部门、角色和有效权限。
3.  读取当前会话的结构化上下文，识别新问题或追问。
4.  从元数据中选择相关表、字段、关系、业务术语和指标定义。
5.  将用户问题、相关
    Schema、必要业务语义及输出约束提交给云端模型，生成候选 SQL。
6.  程序解析 SQL，拒绝不符合只读规则的语句。
7.  校验涉及的表、字段、关联路径和用户权限。
8.  应用可靠的行级权限约束；若无法安全约束则拒绝执行。
9.  检查查询复杂度和资源限制。
10. 通过受限只读连接执行 SQL。
11. 对结果进行行数、大小、字段权限和脱敏处理。
12. 根据数据发送策略，决定是否将结果摘要发送给云端模型生成自然语言回答。
13. 返回自然语言、表格和可选图表；普通用户不展示 SQL。
14. 保存查询状态、执行耗时、结果元信息及必要审计记录。

任何步骤失败都应停止后续执行，并返回适当的用户提示。不能因为模型声称 SQL
安全或正确就跳过程序校验。

### 5.2 Schema 检索与上下文构建

虽然现有字段注释较完整，但不建议默认将 20--100
张表的全部结构和全部业务信息放入每次模型请求。

建议分阶段： 1. 采集表名、字段名、字段类型、注释、主键、外键和索引。 2.
补充业务术语、字段同义词、枚举值含义、指标口径及常用关联关系。 3.
根据用户问题选择相关表和字段。 4. 只将完成该问题所需的 Schema
发送给模型。 5. 记录使用了哪些元数据版本，便于排查问题。

初版可先使用结构化检索、关键词和业务术语映射；是否需要向量检索或混合检索，应由准确率测试决定。

### 5.3 SQL 自动修正流程

1.  首次生成 SQL。
2.  执行静态安全检查。
3.  若是可修正的语法或字段错误，向模型提供经过筛选的错误信息，要求修正。
4.  对修正后的 SQL 从头执行所有安全与权限校验。
5.  达到修正次数上限仍失败，停止并提示用户修改问题或联系管理员。

**暂定建议**：最多自动修正 1--2 次，具体次数需通过测试确定。

禁止将完整数据库凭据、无关业务数据或未经脱敏的敏感查询结果放入修正提示词。对权限拒绝、危险
SQL、资源超限等安全性错误，不应通过反复修改 SQL 尝试绕过限制。

### 5.4 多轮追问与上下文纠正

会话应保存结构化上下文，而不仅是原始聊天文本。建议包含： -
当前业务意图和指标； - 时间范围、筛选条件、分组和排序； -
已识别的业务实体及对应字段； - 当前查询版本与执行状态； -
上一轮查询的摘要和必要的结果元信息； - 元数据版本及上下文创建时间。

示例：

用户："统计本部门上季度的报销金额。" 用户："再按员工分组。"

系统应继承上季度、报销金额和部门范围，并增加员工分组。继承条件仍必须重新通过当前权限校验。若"上季度"定义或指标口径不明确，应先澄清，而不是自行猜测。

上下文纠正需要支持覆盖、追加和移除条件。例如"不是上季度，是本季度"应替换时间条件，而不是把两个条件同时保留。

## 6. SQL 安全与生产数据库保护

### 6.1 只读策略

-   使用专门的 MySQL 只读账号，按所需表授予最小权限。
-   禁止 INSERT、UPDATE、DELETE、DDL、存储过程调用及其他非授权操作。
-   对多语句、注释绕过、危险函数、系统表访问和不支持的语法采取明确策略。
-   不能仅靠正则表达式判断 SQL 是否安全；应使用能够理解 SQL
    结构的解析方案，并对不支持的语法采取默认拒绝。
-   SQL 执行账号、API 密钥等凭据不能发送给大模型。
-   不向普通用户开放可直接执行任意 SQL 的接口。

只读账号是纵深防御的一层，并不替代 SQL 解析、权限控制和查询资源限制。

### 6.2 行级权限实施

这是项目的高风险实现点。可评估以下方法，最终应通过实际 SQL 测试选型：

-   **受控 SQL 改写**：解析 SQL
    语法树，在正确的查询层级注入权限谓词，并验证所有访问路径。
-   **受控查询模板或语义层**：将允许的指标、维度、关联和数据范围转为受控查询表达式，再生成
    SQL。
-   **数据库视图或独立数据服务**：在数据库侧预先提供受限数据视图；但若不同用户需要不同的数据范围，还必须验证视图和身份绑定机制是否可靠。

不能简单地在任意 SQL 的末尾追加 `WHERE dept_id = ...`。这在已有
WHERE、JOIN、子查询、UNION 或聚合的场景中可能失效或改变语义。

如果某条 SQL 无法证明行级权限约束正确，应拒绝执行。

### 6.3 查询资源控制

至少设置以下控制： - SQL 执行超时； - 单次返回行数上限； -
结果集字节数上限； - 最大并发查询数； - 单用户请求速率限制； -
模型调用超时和重试上限； - 连接池容量和等待超时； -
查询成本检查或复杂度限制； - 取消请求时尽可能终止数据库执行。

**暂定初始值，仅供压测起点使用，并非已确认指标：**

  参数                  暂定起点
  ------------------- ----------
  SQL 执行超时             10 秒
  返回行数上限          1,000 行
  自动 SQL 修正次数         2 次
  单用户并发查询         1--2 个
  模型请求超时             30 秒

这些数值需根据生产库负载、典型查询复杂度和业务可接受的等待时间进行验证。不能仅靠
LIMIT 保证查询成本低，因为数据库仍可能扫描或排序大量数据。

### 6.4 生产环境风险控制

生产库直接查询的风险高于查询副本。上线前应： - 与 DBA
确认只读账号权限范围和连接来源； -
评估索引、数据量、慢查询及现有业务负载； -
对允许查询的表和关联关系建立白名单； -
进行慢查询、并发、超时和取消测试； - 设置数据库连接与应用级资源上限； -
明确故障时的熔断和停用流程。

是否使用只读副本属于待决策项。即使已经提供只读账号，也不能据此认定对生产业务没有影响。

## 7. 云端模型与数据保护

### 7.1 模型输入分类

发送云端前，应按数据类别控制信息：

  数据类型             建议策略
  -------------------- ------------------------------------------------
  自然语言问题         检查是否包含个人信息、凭据或敏感业务内容
  表名、字段名、注释   只发送当前查询必要的元数据
  SQL 文本             检查其中是否包含敏感常量或个人数据
  查询结果             默认不发送原始结果；优先本地汇总、脱敏和最小化
  错误信息             去除凭据、内部路径和不必要的业务值
  会话历史             仅发送当前追问所需的最小上下文

### 7.2 自然语言回答策略

推荐先由本地程序完成结果过滤、脱敏和摘要，再决定是否调用云端模型生成回答。

例如，数据库返回部门统计金额后，模型只需接收允许披露的汇总结果和问题，不必接收完整员工明细。

但即使是汇总数据，也可能因小样本、唯一组合或反复追问而泄露个人信息。是否需要最小分组人数、敏感聚合限制等规则，应由业务和安全方确定。

### 7.3 模型服务要求

待选型时需要评估： - API 数据保留及训练使用政策； -
数据处理区域和企业合规要求； - 请求日志与服务商可见范围； - HTTPS、API
密钥保管和轮换； - 超时、限流、故障降级及费用监控； - 模型升级后 SQL
正确率和安全回归测试。

## 8. 元数据与业务语义设计

建议在应用侧维护可版本化的元数据。物理数据库仍是业务数据的权威来源；元数据存储只负责描述数据库结构、业务语义和权限映射。

### 8.1 建议的数据对象

  对象         主要内容
  ------------ --------------------------------------------------
  数据源配置   数据库标识、连接引用、启用状态；凭据单独安全存储
  表元数据     表名、注释、所属模块、是否允许查询
  字段元数据   字段名、类型、注释、敏感等级、展示策略
  表关系       关联字段、关系类型、允许的 JOIN 路径
  业务术语     用户常用词、同义词、对应表字段
  指标定义     指标公式、统计粒度、过滤规则、单位和口径
  字典映射     枚举值与业务名称，例如状态码的中文含义
  权限规则     角色、模块、表、字段、行级规则的映射
  元数据版本   更新时间、来源、发布状态和回滚信息

### 8.2 元数据采集

可从 MySQL 系统元数据读取表、列、索引、主外键和注释。需要注意： -
真实数据库未必声明所有逻辑外键； - 字段注释不一定包含业务口径； -
"金额""状态""创建人"等字段可能在不同模块有不同含义； -
软删除、租户、组织范围等条件必须明确记录。

建议先自动采集，再由业务或开发人员审核业务关系和指标定义。元数据变更后应执行回归测试。

## 9. 数据模型建议

以下为逻辑数据模型，不限定具体 ORM、数据库或物理表名。

  实体                              核心字段 / 关系
  --------------------------------- ----------------------------------------------
  User                              用户 ID、登录标识、部门 ID、角色关联、状态
  Department                        部门 ID、名称、上级部门（如适用）
  Role                              角色 ID、名称、状态
  Permission                        资源类型、资源标识、操作、授权规则
  UserRole / RolePermission         用户与角色、角色与权限的关联
  RowScopeRule                      业务表、关联字段、用户/部门映射、适用范围
  SensitiveFieldPolicy              表、字段、敏感等级、脱敏和模型发送策略
  SchemaTable / SchemaColumn        表字段元数据及版本
  BusinessTerm / MetricDefinition   业务术语、同义词、指标口径
  Conversation                      会话归属、标题、创建时间、共享状态
  Message                           角色、消息内容、时间、关联查询版本
  QueryExecution                    用户、会话、状态、耗时、行数、错误类型
  QueryAudit                        操作类型、主体、目标、结果、时间、追踪 ID
  SharedConversation                被共享会话、授权对象、权限、有效期（如需要）

实际设计时应避免在日志中默认存储完整敏感结果。密码哈希、API
密钥和数据库凭据不得存入普通业务表的明文列。

## 10. API 设计草案

具体路径与请求格式需在技术选型后确定。以下为逻辑接口清单。

  接口能力         说明
  ---------------- --------------------------------------
  登录 / 退出      建立和销毁用户会话
  获取当前用户     返回用户、部门、角色及前端可见功能
  用户管理         创建、停用和维护用户
  部门与角色管理   维护组织与角色信息
  权限管理         配置模块、表、字段和数据范围
  元数据管理       查看、刷新和审核 Schema 与业务定义
  创建对话         建立新的查询会话
  提交问题         触发问题理解、SQL 生成、校验和查询
  获取执行状态     返回执行中、成功、失败或已取消等状态
  获取结果         返回经过权限处理的表格数据和图表配置
  追问             基于当前会话上下文继续提问
  查询历史         获取当前用户有权查看的历史
  共享会话         创建、查看、撤销授权共享
  审计查询         仅向获授权的管理员或审计角色开放

所有接口都必须在服务端执行身份认证和授权，不能信任前端传来的用户
ID、部门 ID 或权限标记。

## 11. 查询历史、审计与可观测性

### 11.1 查询历史

建议保存： - 用户问题及时间； - 会话 ID 和查询版本； -
查询状态、耗时、返回行数； - 结果摘要或必要的展示元信息； -
失败类型和追踪 ID； - 共享授权信息。

是否保存原始
SQL、完整模型请求和响应、结果快照及保存期限，需要进行数据最小化评审。普通用户不展示
SQL，并不意味着后台完全不记录
SQL；后台记录也必须限制访问和保护敏感内容。

### 11.2 审计事件

至少考虑： - 登录成功和失败； - 用户、角色、权限配置变更； -
查询提交、SQL 被拒绝、查询执行和取消； - 自动修正触发及最终结果； -
敏感字段访问和脱敏； - 查询历史共享和撤销； - 模型调用失败、超时和限流。

日志应包含关联追踪
ID、用户主体、事件类型、时间和结果状态。日志不得记录密码、API
密钥等凭据；敏感查询参数应按策略脱敏。

### 11.3 监控指标

-   查询成功率、失败率、P50/P95 响应时间；
-   SQL 执行耗时、超时次数和慢查询；
-   当前并发数、连接池占用和拒绝次数；
-   模型调用耗时、失败率、token 用量和费用；
-   SQL 自动修正成功率；
-   权限拒绝次数和安全校验失败类型。

## 12. 部署与运维设计

### 12.1 部署建议

【已确认】优先 Docker Compose。

【暂定方案】可先将
Web/API、查询编排服务和管理功能作为一个或少量应用服务部署，避免在用户规模尚小的情况下过度拆分。数据库仍使用现有
MySQL；应用侧的元数据、用户、会话和审计存储应根据技术选型确定，不能默认必须新增某一种数据库。

### 12.2 配置与密钥

-   数据库只读凭据、模型 API 密钥不得写入镜像或提交到代码仓库。
-   生产配置应通过受控环境变量、密钥文件或企业密钥管理方式注入。
-   设置非 root 容器用户、网络访问限制、健康检查和资源限制。
-   持久化用户、权限、会话及审计数据，并制定备份和恢复方案。
-   生产数据库只允许应用服务通过必要网络路径访问。
-   明确镜像更新、配置变更、回滚及故障停用流程。

### 12.3 环境区分

建议区分开发、测试和生产配置。测试环境使用脱敏或合成数据验证 SQL
与权限规则；不能仅在生产环境通过人工抽查来验证行级权限。

## 13. 测试与验收

### 13.1 功能测试

-   自然语言问题可以映射到正确的表和字段；
-   常见过滤、排序、聚合和 JOIN 能正确执行；
-   返回自然语言、表格和图表；
-   支持追问、条件替换和上下文纠正；
-   普通用户不展示 SQL；
-   个人历史及授权共享按权限工作；
-   SQL 错误可有限次数修正，超限后安全退出。

### 13.2 安全测试

-   INSERT、UPDATE、DELETE、DDL、多语句和其他非授权操作均被拒绝；
-   未授权表和字段不能通过 JOIN、子查询或别名绕过；
-   行级权限在聚合、分组、子查询、排序及多轮追问中保持有效；
-   无权限用户不能从错误消息、图表、历史或共享快照中获得敏感数据；
-   模型请求和响应不包含禁止发送的数据；
-   不能通过修改前端参数伪造用户身份或部门；
-   权限变更后，旧会话不能沿用已失效权限。

### 13.3 性能与稳定性测试

-   查询超时后能终止或停止继续占用资源；
-   超过行数或字节数限制时能安全截断或拒绝；
-   达到并发上限时按策略排队或拒绝；
-   模型超时、API 限流和数据库不可用时能给出可理解的错误；
-   取消、重试和重复提交不会造成无限执行；
-   通过模拟并发和慢查询验证生产库保护措施。

### 13.4 验收指标

以下目标需要在业务评审后确定，当前不应把具体百分比视为承诺。

  指标         验收方式
  ------------ ----------------------------------------------
  SQL 正确率   使用人工标注的业务问题集评估
  权限正确性   对各角色、部门和敏感字段建立测试矩阵
  安全性       所有设计范围内的越权与危险 SQL 测试通过
  性能         定义目标并发、P95 响应时间和超时比例
  稳定性       验证模型、数据库及网络故障下的降级
  可追溯性     查询、修正、执行和拒绝事件可通过追踪 ID 关联
  用户体验     业务人员能够完成指定的典型查询任务

## 14. 实施阶段建议

### 阶段一：需求与数据盘点

-   确认业务模块、典型问题和高频指标；
-   盘点表、字段、关联关系、字典及敏感字段；
-   梳理用户、部门、角色和行级权限规则；
-   与 DBA 评估生产库查询风险。

### 阶段二：最小可用查询链路

-   完成登录和基本权限；
-   完成 Schema 采集与相关表选择；
-   实现 SQL 生成、解析、校验和受限只读执行；
-   先使用有限的业务表进行验证。

### 阶段三：权限与安全完善

-   实现并测试表级、字段级、行级控制；
-   完成敏感字段策略、查询限流、审计和异常处理；
-   建立权限回归测试集。

### 阶段四：对话与展示

-   实现自然语言回答、表格和图表；
-   实现多轮追问、条件纠正、查询历史及授权共享；
-   验证共享历史不会泄露无权访问的数据。

### 阶段五：测试、部署与试点

-   在测试环境完成安全、性能和准确率评估；
-   使用 Docker Compose 部署；
-   选择少量业务用户试点；
-   根据错误样本修正业务术语、Schema
    关联和提示策略，再逐步扩大使用范围。

## 16. 关键风险与上线门槛

上线前必须验证以下事项：

1.  **生产数据库安全**：只读账号权限最小化，查询成本与并发受控。
2.  **行级权限可靠**：无法通过 JOIN、子查询、聚合和追问绕过。
3.  **云端数据保护**：发送模型的数据经过最小化、授权检查及必要脱敏。
4.  **权限与历史一致**：共享会话和历史结果不会成为越权访问渠道。
5.  **异常安全退出**：模型失败、SQL
    解析不支持、权限映射缺失或资源超限时默认拒绝执行。
6.  **审计可追踪**：可以关联用户、会话、查询版本、执行结果和安全事件。

任一 P0 安全事项未完成验证，不建议直接向全部业务用户开放生产查询。

## 17. 结论

本项目的核心不是单独调用大模型生成
SQL，而是构建一条可控、可审计的自然语言数据查询链路。

建议优先解决三项基础能力：

1.  **业务元数据与指标定义**：使模型知道该查哪些表、字段和业务口径。
2.  **权限约束与安全执行**：确保生成的 SQL 始终处于当前用户授权范围内。
3.  **生产查询保护与评估**：确保系统不会因为复杂 SQL
    或高并发影响现有业务。

在完成 P0 待决策事项后，再冻结技术栈、接口规范和具体实现方案。
