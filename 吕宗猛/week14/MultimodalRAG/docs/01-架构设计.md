# MultimodalRAG 架构设计

## 1. 目标与范围

### 1.1 功能目标

| 编号 | 功能 | 验收口径 |
|---|---|---|
| F1 | 前端上传多个 PDF，经 Kafka 到后端，后端用 MinerU 解析并存储 | 多选上传后 Kafka 有消息，MySQL 有文档记录，解析产物落磁盘 |
| F2 | 前端展示解析状态：待解析、解析中、解析完成 | SSE 实时更新，状态与数据库一致 |
| F3 | 多模态问答：输出图文混排；用户图问一起送 LLM | 回答含 Markdown 图片标签；用户上传图片能被模型理解并回答 |
| F4 | 会话记录保存、可点击继续；输入框支持直接粘贴图片；用 LLM 生成会话标题 | 左侧会话列表可加载历史消息；Ctrl+V 出现图片预览；新会话标题由 LLM 摘要生成 |

### 1.2 已确认决策

| 项 | 决策 |
|---|---|
| 项目目录 | `week14/MultimodalRAG` |
| 后端目录 | `app/` |
| 文档目录 | `docs/` |
| MySQL | 复用 `rag-mysql` 实例，新建 `rag_mm` 库 + 专用用户 |
| 部署 | Kafka + api + worker + web + MinerU 全部部署到飞牛 |
| MinerU | 4.2.1，`basic` CPU 档 |
| Embedding | 复用 `rag-models` 的 `bge-small-zh-v1.5`，512 维 |
| 图片 | PDF 图片直接作为独立资源保存，Markdown 中用图片标签引用 |
| 检索后 | 将图片与周围文本一起送入 LLM，让其摘要并回答 |
| 状态 | SSE 实时推送 |

## 3. 组件职责

| 组件 | 职责 |
|---|---|
| Web | 左侧导航与会话列表、上传 PDF、状态表格、聊天窗口、SSE 客户端、Ctrl+V 粘贴图片 |
| api | 接收上传、写 MySQL、投 Kafka、查询状态、检索、组装多模态请求、调用 Magpie、SSE |
| worker | 消费 Kafka，调 MinerU，解压图片/markdown，切块，调 embedding，写 MySQL |
| Kafka | 解耦上传与解析，支持多 worker 水平扩展 |
| MinerU | PDF → Markdown + 图片 ZIP（`/v1/file_parse`） |
| MySQL `rag_mm` | 文档、块、图片、会话、消息 |
| rag-models | bge-small-zh-v1.5 文本向量化（512 维） |
| Magpie | OpenAI 兼容多模态聊天网关 |

## 4. 关键流程

### 4.1 上传与解析

1. 前端 `POST /api/documents/upload`（multipart，多文件）。
2. api 校验扩展名/大小，保存到 `/data/uploads/{uuid}.pdf`。
3. api 插入 `mm_document(status='pending')`，并向 `mm.pdf.parse` 发送 `{doc_id, file_name}`。
4. worker 消费消息，状态改为 `parsing`。
5. worker 调 MinerU `POST /v1/file_parse`（`tier=basic`，`output_formats=default`，`wait_timeout=3600`）。
6. MinerU 返回 ZIP：`markdown.md`、`middle_json.json`、`images/`。
7. worker 保存图片到 `/data/parsed/{doc_id}/images/`，重写 Markdown 图片标签为 `/api/documents/{doc_id}/images/{name}`。
8. worker 按标题/段落切块，记录每个 chunk 的 `image_ids`。
9. worker 调 `rag-models` `/v1/embeddings`，批量向量化，写 `mm_chunk.embedding`（float32 BLOB）。
10. 状态改为 `completed`，写入 chunk/image 计数与 `parsed_at`。

### 4.2 状态 SSE

- `GET /api/documents/events` 返回 `text/event-stream`。
- api 每秒查询一次当前文档快照，计算 SHA-256，变化时推送 `event: documents`，内容为完整文档列表。
- 客户端 `EventSource` 监听并覆盖表格数据；前端无需轮询。

### 4.3 多模态问答

1. 前端 `POST /api/chat/ask`（multipart：`session_id`、`question`、可选 `image`）。
2. api 用问题文本调 `rag-models` 向量化，在 `mm_chunk` 中做余弦相似度 top-k。
3. 对每个检索到的 chunk：
   - 取 chunk 文本；
   - 取 `image_ids` 对应的图片文件；
   - 按“文本块 → 图片 → 下一文本块”的顺序拼成一条多模态 user message。
4. 如果用户上传了图片，作为额外的 `image_url` 内容块附加在同一 user message。
5. 调 Magpie `/v1/chat/completions`，模型为 `workbuddy/deepseek-v4.1-flash`。
6. 模型可在回答中输出 `[[img:图片ID]]`；api 校验 ID 后替换为 Markdown 图片标签；若模型未输出标记，自动附上检索到的相关图片。
7. 保存用户消息与助手消息，返回答案、参考来源、图片列表。

## 5. 技术栈

| 层 | 选型 |
|---|---|
| 前端 | Vue3 + Vite + Element Plus + markdown-it |
| 后端 | FastAPI + SQLAlchemy + PyMySQL + aiokafka + httpx |
| 消息 | Apache Kafka 3.9.1（KRaft 单节点） |
| 解析 | MinerU 4.2.1（`basic` CPU，api-server + file-parse-server） |
| 向量 | bge-small-zh-v1.5（复用 rag-models，512 维） |
| LLM | Magpie `workbuddy/deepseek-v4.1-flash` |
| 数据库 | MySQL 8.0（`rag_mm`） |

## 6. 非目标

- 不做多租户、登录、RBAC。
- 不做 PDF 以外的文档格式。
- 不做向量数据库（当前数据量用 MySQL BLOB + 内存余弦即可）。
- 不做文档删除/版本管理（MVP 只做上传、解析、问答）。
