## 1. 项目概述

### 1.1 项目背景
企业内部业务人员存在大量临时取数、看数、做分析的需求，传统模式依赖数据开发或分析师编写 SQL，沟通成本高、响应慢。本项目构建一个 **ChatBI Agent**，让业务人员通过自然语言对话即可完成取数、制图、生成分析报告，降低数据使用门槛，提升决策效率。

### 1.2 产品定位
- **形态**：独立 Web 应用，聊天式交互，查询结果在对话流内以「表格 + 图表 + 分析文本」返回。
- **使用对象**：公司内部业务人员（非技术背景为主）。
- **数据源**：MySQL（MVP 单数据源，架构预留多源扩展）。
- **核心能力**：自然语言转 SQL（NL2SQL）、自动生成图表、自动生成分析报告、多轮对话追问、SQL 手动修改与执行。

### 1.3 目标与边界（MVP）
**一期必须达成：**
- 自然语言 → 合法且安全的 SQL → 执行 → 表格/图表/报告全链路跑通。
- 行权限 + 列权限双重控制，数据不越权。
- 高危 SQL 拦截、查询限流、结果集上限控制。
- RAG 检索数据字典辅助 NL2SQL，降低幻觉。
- 会话持久化、报表收藏、审计日志全链路留存。

**一期不做（后续迭代）：**
- 私有化部署、多租户 SaaS。
- 数据脱敏/合规审计专项。
- MCP 具体业务对接与鉴权（仅预留接口与扩展点）。
- 模型失败自动切换、日志自动归档清理。

| 能力 | 说明 | 优先级 |
|---|---|---|

## 3. 核心业务流程设计

### 3.1 NL2SQL 主链路（方案 B：先选表字段，再生成 SQL）

```
用户提问
   │
   ▼
① 会话上下文装载（历史问题+SQL+结果摘要，不带明细）
   │
   ▼
② 权限上下文装载（当前用户的角色、行过滤条件、可见字段集合）
   │
   ▼
③ RAG 检索元数据（已按列权限过滤，只返回有权字段）
   │
   ▼
④ LLM 先选表、选字段（结构化输出：候选表、候选字段、口径理解）
   │
   ▼
⑤ 表/字段合法性校验（与元数据库核对，拦截幻觉表/字段）
   │  ──失败──▶ ⑥ 反问澄清 or 修正
   ▼ 成功
⑦ LLM 生成 SQL（注入行权限过滤条件）
   │
   ▼
⑧ SQL 安全校验（语法解析 + 高危规则拦截 + 行权限确认）
   │  ──被拦截──▶ 向用户说明原因，提供修正建议
   ▼ 通过
⑨ 执行查询（限流、超时、结果集上限控制）
   │
   ▼
⑩ 结果缓存（key 绑定用户权限上下文）
   │
   ▼
⑪ 结果解读 + 图表配置生成 + 报告生成
   │
   ▼
⑫ 对话内返回「表格 + 图表 + 分析文本」
```

### 3.2 错误处理与自动纠错
- SQL 执行报错时，**最多自动重试 5 次**。
- 每次重试将「上一轮 SQL、数据库报错原文、已检索到的 RAG 上下文」全量回传给大模型，要求修正 SQL 后再生成。
- 5 次仍失败：停止重试，向用户呈现最终报错信息、已尝试的修正过程、以及人工建议（如联系数据团队）。
- 重试过程同步写入审计日志。

### 3.3 歧义澄清流程
- 当 LLM 判断问题存在歧义（缺少时间范围、维度不明、指标口径有多个候选），**优先反问用户澄清**，不直接生成 SQL。
- 反问以结构化卡片呈现（候选选项 + 自由输入），用户确认后继续链路。
- 判定触发条件（后台可配置）：候选表数量 > N、候选指标口径冲突、缺少关键时间/维度约束。

## 4. 功能模块详细设计

### 4.1 对话与问答模块
- 交互形态：聊天窗口为主，问题在对话流内依次展示「SQL 片段（可折叠）→ 表格 → 图表 → 分析文本」。
- 支持 Markdown 渲染，支持 SQL 代码高亮与复制。
- 用户可对生成 SQL 手动编辑，提交后重新走完整校验流程执行。
- 每轮回答可附「查看 SQL」「重新查询」「收藏」操作按钮。

### 4.2 NL2SQL 引擎
- 采用「选表选字段 + 生成 SQL」两阶段 Prompt 结构。
- 输出约束为结构化 JSON（表名、字段名、条件、聚合、时间范围），便于程序化校验。
- 表/字段合法性校验：生成候选表/字段后，与元数据服务实时比对，命中不存在的表/字段立即拦截并触发修正或反问。
- 指标口径：从 RAG 检索出的指标说明中理解，口径冲突时进入澄清流程。

### 4.3 RAG 检索模块
- **检索内容**：仅数据字典（表名、表注释、字段名、字段注释、字段类型、指标口径、枚举值说明），一期不存放业务文档。
- **检索策略**：混合检索（向量 + 关键词），结果全量喂给大模型，不做摘要压缩。
- **权限过滤**：检索前先过滤当前用户无权限的字段，模型从一开始看不到无权字段（列权限方案 B）。
- **配置参数**（后台可配，初始值见附录）：topN = 8，相似度阈值 = 0.65。

### 4.4 元数据管理
- 数据来源：MySQL 的 `information_schema` 与数据字典表。
- 同步策略：**定时增量同步**（默认每 30 分钟，可配）；表结构变更自动感知并更新向量库。
- 变更处理：字段新增/删除/类型变更 → 增量更新对应表的向量条目。
- 全量重建：仅管理员手动触发（大版本变更、数据字典重构时使用）。
- 同步失败：记录告警日志（MVP 先落日志，预留企业微信/邮件通知通道）。

### 4.5 图表渲染
- 图表库：**ECharts**（自研调研结论：功能全、生态成熟、中文文档完善、社区资源多）。
- 图表类型：由大模型根据查询结果自动判断（折线、柱状、饼图、面积、雷达、散点等），用户在对话内可手动切换图表类型。
- 图表配置由 LLM 生成标准 JSON（type、xAxis、series 映射），前端渲染。
- 指标与维度字段自动映射：数值字段→series，时间/分类字段→xAxis。

### 4.6 分析报告生成
- 输出形态：对话内富文本（Markdown 渲染），**不支持导出** Word/PDF（MVP）。
- 报告内容：数据结论、趋势描述、关键发现、异常提示、口径说明。
- 报告引用对话内表格/图表数据，由 LLM 基于查询结果摘要生成，不做长文写作。
- 报告与 SQL、图表配置一同保存，供收藏与复盘。

### 4.7 会话管理
- 会话支持创建、命名、恢复继续提问（多轮上下文）。
- 会话持久化到数据库，用户下次登录可继续之前的分析。
- MVP 暂不做会话分组，仅支持会话列表 + 命名；会话永久保留，管理员后台可清理。
- 每个会话内上下文携带：历史问题、历史 SQL、结果摘要（**不含原始明细数据**），防止上下文超长与数据泄露。

### 4.8 报表收藏
- 收藏内容：原始提问、生成 SQL、图表配置、分析报告。
- **不持久化查询明细结果**：每次打开收藏报表，按当前用户权限重新查询（命中缓存则走缓存）。
- 收藏报表支持二次编辑 SQL、重新执行、重新生成图表与报告。

## 5. 权限体系设计

### 5.1 总体设计
- 独立 RBAC 权限体系（不依赖公司现有系统，MVP 自建）。
- 模型：用户 User → 角色 Role → 权限资源。
- 权限资源分为两类：**行权限（数据范围）**、**列权限（字段可见性）**。

### 5.2 用户与角色
- 用户属性（dept_id、职级、区域等）：登录时写入会话上下文，来源于用户主表。
- 角色管理：后台配置角色、绑定权限、绑定可用模型列表。

### 5.3 行权限（Row-level Security）
- 配置形式：角色绑定「表 + 过滤条件」，条件支持当前用户上下文变量。
- 示例：`订单表: dept_id = ${current_user.dept_id}`、`区域表: region IN (${current_user.regions})`。
- **注入方式**：NL2SQL 生成 SQL 时，自动将行权限过滤条件拼入 WHERE 子句；SQL 校验阶段二次确认过滤条件存在且未被绕过。

### 5.4 列权限（Column-level Security）
- 采用 **方案 B 为主 + 方案 A 兜底** 双层防护：
  1. **源头层（主）**：RAG 检索阶段直接过滤掉当前用户无权限的字段，模型不生成无权字段。
  2. **校验层（兜底）**：SQL 生成后，解析 SQL 中的 SELECT 字段，与权限字段集合二次比对，出现无权字段立即拦截。
- 控制粒度：角色 → 表 → 字段可见性（可见/隐藏）。

### 5.5 权限校验时序
```
用户请求 → 加载用户角色 → 计算可见字段集 & 行过滤条件
        → RAG过滤 → SQL生成(注入行权限) → SELECT字段校验(列权限)
        → 行权限条件确认 → 执行
```

### 6.2 缓存 Key 设计
- Key 结构：`chatbi:result:{user_permission_hash}:{question_hash}`。
- `user_permission_hash` 为当前用户「可见字段集 + 行过滤条件」的哈希，**同一问题不同权限用户不共用缓存**。

- 默认过期：30 分钟（可配）。

## 7. 缓存与性能设计

### 7.1 缓存策略
- 命中判定：问题语义归一化 + 权限上下文哈希一致才命中。
- **黑名单机制**：支持后台配置禁止缓存的表/指标（敏感、实时高频变动），命中黑名单则不缓存、不读缓存。
- **缓存管理后台**：查看缓存条目、单条删除、一键清空。
- 手动改 SQL 后执行的结果，不写入缓存（避免污染）。

### 7.2 性能指标（MVP，100 并发）
| 指标 | 目标值 |
|---|---|
| 在线用户 | 100 |
| 查询响应（P95） | ≤ 8s（含 LLM 链路） |
| 缓存命中查询响应 | ≤ 1s |
| 元数据同步频率 | 30 min（可配） |

## 8. 安全与审计设计

### 8.1 SQL 安全校验（前置强拦截）
- 使用成熟 SQL 解析组件（如 `sqlparser` / 阿帕奇 Calcite / jsqlparser）做语法解析与结构分析。
- **高危规则拦截（硬规则，不可绕过）：**
  - DDL：CREATE / DROP / ALTER / TRUNCATE 等。
  - DML 变更：INSERT / UPDATE / DELETE。
  - 危险函数：`LOAD_FILE`、`SLEEP`、`INTO OUTFILE`、存储过程调用等。
  - 多语句执行（SQL 注入防护）。
  - 全表扫描（无 WHERE 且无 LIMIT 的大表查询）。
  - 无 LIMIT 上限的查询。
- 校验通过后执行，执行前再行权限确认。
- **用户手动修改的 SQL，同样完整重走权限校验 + 安全校验**，不设白名单放行。

### 8.2 执行控制
- 查询超时：默认 30s（可配）。
- 结果集上限：默认最大返回 2000 行，超限拒绝执行并提示（后台可配）。
- 并发限流：按用户/全局 QPS 限流，防止打爆 MySQL。

### 8.3 审计日志
- 全字段留存（见 6.1 审计表），**不脱敏**。
- **永久保存**（MVP），后续合规要求可增加归档清理策略（二期）。
- 提供审计日志后台查询界面（按用户/时间/SQL 关键字筛选）。

## 9. 模型与 RAG 设计

### 9.1 模型管理
- 使用**国内大模型**（如通义千问、DeepSeek、豆包等），通过 OpenAI 兼容协议接入。
- 支持**多模型注册**：可配置多个模型，供不同链路/角色使用。
- 模型角色划分：
  - **理解/选表模型**：意图理解、表字段选择。
  - **生成 SQL 模型**：SQL 生成与纠错。
  - **解读/报告模型**：数据解读、报告生成。
  - （MVP 可先用同一模型承载多角色，架构上支持分离）
- **模型切换权限**：管理员给角色分配可用模型列表，普通用户只能在角色允许范围内选择，不可随意切换。
- **超时控制**：单次调用默认 60s；超时返回友好提示，一期**不自动切换模型**（降级到二期）。

### 9.2 RAG 设计
- Embedding 模型：国内开源/商用 embedding（如 bge-m3 等）。
- 向量库：Milvus（或 Elasticsearch 向量检索）。
- 内容：数据字典（表/字段/指标口径）。
- 检索：混合检索（向量 + 关键词 BM25），topN=8，阈值 0.65。
- 权限联动：检索前过滤无权字段（方案 B）。

### 9.3 幻觉缓解措施
1. RAG 提供真实元数据上下文。
2. 两阶段链路（先选表字段、校验通过后再生成 SQL）。
3. 表/字段合法性实时校验。
4. SQL 解析校验。
5. 执行报错自动重试修正（5 次）。
6. 结果解读基于真实查询结果，而非凭空生成。

## 10. MCP 扩展设计

### 10.1 定位
- 本系统作为 **MCP Client**，预留能力，后续可对接外部 MCP Server（第三方工具、其他数据源、业务系统）。
- MVP 阶段**不对外暴露本系统为 MCP Server**，MCP 鉴权暂不实现（仅预留接口与扩展点）。

### 10.2 设计原则
- Agent 编排层抽象「工具调用」接口，MCP 作为其中一种工具提供者实现。
- 预留 MCP Server 注册表、工具描述元数据、调用结果回传的标准化结构。
- 一期仅落地接口与占位实现，二期做具体业务对接与鉴权打通。

## 13. 非功能需求
- **可用性**：核心链路（对话、查询）可用性 ≥ 99%。
- **性能**：见 7.2。
- **安全**：高危 SQL 零放行；越权查询零发生（行/列权限双校验）。
- **可维护性**：配置项后台化，不硬编码（见附录配置清单）。
- **可观测性**：全链路审计日志 + 执行耗时监控。

## 14. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| LLM 生成 SQL 幻觉（错表/错字段） | 查询失败、口径错误 | 两阶段链路 + 实时校验 + RAG |
| 权限绕过 | 数据越权泄露 | 列权限双层 + 行权限注入校验 |
| 大表全表扫描拖垮库 | 数据库性能 | 高危拦截 + LIMIT 强制 + 超时 + 限流 |
| 大模型输出不稳定 | 口径不一致 | 结构化 JSON 输出 + 校验 + 重试 |
| 上下文超长 | 成本高、性能差 | 上下文只带摘要不带明细 |
| 缓存数据过期/越权 | 结果错误或泄露 | 权限上下文哈希 + 黑名单 + 30min 过期 |
